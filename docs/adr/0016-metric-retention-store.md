# ADR-0016 · 本地指标留存用单文件 SQLite，不用 TSDB

- 状态：**已采纳**（2026-11-05）
- 关联：`docs/09-observability.md` §4、`FR-MON-05`

## 背景

`FR-MON-05` 要求「指标留存与本地趋势（轻量时序，非 TSDB），保留 7 天可查」。它同时是
「容量增长」与「告警」的前置：没有历史，就谈不上一周涨了多少，也谈不上「连续 3 次采样
超过阈值」。

单机工具不能为了画四条曲线引一套 TSDB：那带来常驻进程、额外端口与运维成本，而本工具
的定位是「打开面板的时候才有数据」。

## 决策

1. **存储形态**：一个 SQLite 文件（`modernc.org/sqlite`，纯 Go，不违背后续免 CGO 的约束），
   表结构照 `docs/09 §4` 的两张窄表（`metric_sample` / `slow_query_hourly`）。
2. **采样时机**：只在**面板打开时**写入，由 `/monitor/metrics` 的读取顺手记一条。
   面板关闭就停——这与前端「每 5 秒轮询」的节奏天然一致，也是文档明确要的取舍。
3. **时间粒度**：按分钟对齐（`ts = unix 秒 / 60 * 60`），主键 `(connection_id, metric, ts)`，
   写入用 `INSERT OR REPLACE`：同一分钟多次读只留最后一条，避免把文件撑大。
4. **保留策略**：7 天，**每天最多清理一次**（进程内记住上次清理时间），删 `ts < now-7d`。
5. **可达性**：`serve -metrics <path>` 指定文件；不指定就**不留存**，此时历史端点返回
   `available: false` 而**不是**假装有数据。

## 后果

- 好处：零新依赖（sqlite 已在用）、零常驻进程、文件可直接删。
- 代价：数据点只在用户关心时才存在，趋势会有空缺——文档已写明这是有意取舍，不是缺陷。
- 风险：并发写。单进程内用一把互斥锁串行化写入（本工具的读路径本来就是低频的）。
- 迁移：文件带 `PRAGMA user_version`，改表结构时按版本升。**v1 只写 1**。

## 备选（未采纳）

- **JSONL 追加**：简单，但按窗口查询要全文件扫描，7 天数据量下会明显卡。
- **引 Prometheus 客户端 / TSDB**：为一个单机工具引入常驻组件，收益与成本不成比例。
- **常驻采集**：会持续向生产库发查询，而用户在没打开面板时并不需要趋势。

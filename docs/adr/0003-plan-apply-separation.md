# ADR-0003 · 变更必须 Plan / Apply 分离

- 状态：**已采纳**
- 日期：2026-11-02
- 影响面：`service/change`、数据编辑、结构设计、迁移、Agent

---

## 背景

数据库工具的核心风险是「一个动作直接改变了生产数据，而操作者事先不知道会发生什么」。

常见做法是「点保存 → 执行 → 弹个确认框」。确认框通常只写「确定要执行吗？」，用户已经形成了无脑点「是」的习惯。这不是保护，是仪式。

---

## 决策

**所有写操作强制两步：先生成 `ChangePlan`，再 `Apply`。**

```
生成 Plan                       Apply
─────────                       ─────
· 正向语句                       · 校验 approval 与 statement_hash 一致
· 回滚语句（或标记不可逆）        · 校验 preconditions（对象未变、无长事务）
· 影响评估（行数/锁/时长）        · 执行
· 风险分级                       · 逐语句校验影响行数
· 可执行的替代建议                · 记审计
```

### 具体规则

1. `Apply` 必须携带 `approval_id`（`autonomous` 模式下的豁免也生成一条 recorded approval）。
2. `Apply` 时重新计算语句哈希，与审批时的哈希比对；不一致即拒（防「审批 A、执行 B」）。
3. `Approval` 有效期 10 分钟，过期需重新确认。
4. `risk >= R3` 且 `rollback` 为空 → 标记 `irreversible`，要求输入对象名确认。
5. `applied` 的 plan 不可修改，只能 `rollback`（生成反向 plan 并走同样的流程）。
6. **迁移的每一步 DDL 也走这个流程**（可批量审批，但不跳过）。
7. 数据网格的「提交变更集」在内部就是一个 plan。

---

## 理由

### 为什么必须分离（而不是一个接口带 `dry_run` 参数）

`dry_run` 参数的问题是：它只是同一条代码路径上的一个分支，很容易被遗忘、被默认值覆盖、被调用方绕过。

分离成两个 API 后：

- **类型系统帮你强制**：没有 `plan_id` 就无法调用 `apply`。
- **审批记录天然存在**：因为 `apply` 必须引用一个已存在的 plan。
- **UI 与 Agent 的交互被统一**：都必须是「看 → 确认 → 执行」。
- **可审计**：plan 本身是一条记录，包含当时的判断依据。

### 为什么回滚要先生成（而不是事后想办法）

事后生成回滚需要在失败时重新推导原始状态，此时信息可能已经丢失（例如 `DROP COLUMN` 之后，列定义还在元数据里，但数据已没了）。

事前生成回滚，至少能强制工具回答一个关键问题：**这个操作能不能回滚？**

于是有了三类明确的语义：

| 类别 | 引擎 | 回滚真实性 |
|---|---|---|
| `transactional` | PG、SQLite、多数 MSSQL DDL | 真实回滚（失败即全部撤销） |
| `compensating` | Oracle DDL | 补偿语句，可能不完整 |
| `lossy` | MySQL DDL | 补偿语句，**可能永久丢数据** |

这个分类必须暴露给用户，而不是含糊地说「可以撤销」。

### 为什么要有影响评估

「会影响 12 万行」和「会影响 3 行」是完全不同的决策。没有数字，审批就是盲签。

评估精度分级：`exact`（COUNT 得出）/ `estimated`（统计信息）/ `unknown`。UI 必须标注，不能把估算伪装成精确。

### 为什么 approval 要绑定 statement_hash

没有绑定，审批就只是「允许这个 plan id 执行」。若 plan 在审批后被修改（无论是人改的还是 Agent 改的），审批就失效了——但用户以为还有效。

绑定哈希把「审批的是这个内容」变成可验证的事实。

---

## 后果

**正面**

- 危险操作有了统一的、无法绕过的关口。
- 回滚能力被前置到设计阶段，而不是事后补救。
- 审计天然完整（每个 plan 是一次决策记录）。
- Agent 与人工的行为一致（见 ADR-0002）。

**负面 / 需要承担**

- 交互多一步。对「改一个单元格」这种小操作也走 plan，需要 UI 上做成「内联预览 + 一次确认」，不能让用户感觉在填表。
- 回滚生成的工作量大，且各引擎语义不同（MySQL 的补偿回滚尤其难做对）。
- `preconditions` 的检查有竞态（检查通过后、执行前对象被改），无法完全消除；只能靠执行时的 `statement_hash` 与引擎报错兜底。
- 长事务场景下 `Apply` 可能长时间阻塞，需要进度与取消。

**约束（必须持续遵守）**

- 禁止任何绕过 `plan` 直接执行 DDL/DML 的路径（含内部迁移、修复脚本）。
- 新增引擎时，必须实现该引擎的 `rollback_kind` 判定，不允许一律 `compensating` 含糊处理。
- `plan` 的影响评估若为 `unknown`，风险等级至少提升一级。

# ADR-0009 · 备份续跑用「表级分段 + 侧车检查点」，不改容器格式

- 状态：**已采纳（实现待做）**
- 日期：2026-11-05
- 影响面：`internal/service/backup.go`（`Backup` 增加续跑）、`cmd/dbrover`（`-resume`）、`docs/08`

---

## 背景

DBR 容器 v1 已落地（`docs/08 §7`）：`magic + version + flags + header_len + header JSON + 每段（u32 长度 + 该表的 sql 脚本）`。

验收第 2 条要求「备份中途 kill 进程，重启可续跑且不重复」。这带来一个必须现在回答的问题：**要不要为了续跑改容器格式？** 一旦有真实的备份文件落在用户机器上，改格式就要写迁移，代价远高于现在。

## 决策

**不改格式。续跑以「表」为粒度，检查点放在侧车文件里。**

- 每个 section 仍然是一张表的完整脚本，顺序追加、带长度前缀——这两条性质本来就让文件可以按表边界截断。
- 写完一张表就更新侧车 `<file>.progress`（每行一条 JSON：`{"table":"...","end_offset":N}`），用「写临时文件 + 原子改名」避免半截记录。
- 续跑时：读侧车 → 把容器 `Truncate` 到最后一条记录的 `end_offset` → 跳过已完成的表继续写。
- 容器版本号保持 `1`，读端不需要任何改动。

**为什么不做行级续跑**：那需要分块表（块偏移索引）与块级校验，容器格式要升到 v2，而且恢复端也得跟着支持部分块。收益是一张失败的大表少读一部分——相对复杂度不值得。表级续跑已经能让「99 张表跑完 98 张」的场景免于重来。

## 后果

**正面**

- 现在就能实现验收第 2 条，不需要格式迁移。
- 读端（`inspect`、未来的恢复）完全不变。

**负面 / 需要承担**

- 一张表中途失败要重导整表。表越大越痛，但这是可解释的取舍，不是隐藏行为。
- 侧车丢了就只能整库重跑；**必须**在 CLI 里明确说这句，而不是静默从头开始（否则用户会以为续跑了）。

## 验证计划（实现时按这个写）

1. 用一个在写入第 K 字节后必定失败的 `io.Writer` 模拟 kill，产生不完整容器 + 侧车。
2. 用真实 `*os.File` 续跑：断言最终容器列出的对象数等于全量、**同一张表不出现两次**（按段名去重）。
3. 删掉侧车再续跑：必须明确报错「找不到检查点，需整库重跑」，不许静默从头。
4. 截断后文件的最后一个 section 必须完整：读回该段脚本并回放一次，确认不是半截。

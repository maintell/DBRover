# ADR-0011 · 迁移数据搬运：主键键集续跑、全量哈希校验、流式批插

- 状态：**已采纳（部分实现）**：行规范化编码与整表摘要已落地（`internal/service/migrate_hash.go`，`TestCanonicalValue` / `TestTableDigest`）；键集搬运与检查点未做
- 日期：2026-11-05
- 影响面：`internal/service/migrate_exec.go`（新增）、`docs/08 §4`

---

## 背景

`docs/08` 验收第 6、7 条要求「2 万行中途 kill 后可续跑、目标行数与源一致且无重复」和「能发现被篡改的 1 行」。这三件事互相牵制：

- 要续跑，就得有稳定的推进键；
- 要发现篡改，就得有可比的指纹；
- 不能把整表读进内存——大表会直接把进程打爆。

## 决策

### 1. 续跑粒度：主键键集（keyset），不是行号

按主键键集推进：每批 `WHERE pk > :last ORDER BY pk LIMIT :n`，批末把 `last` 写进检查点。

- **单列主键**：`pk > ?`；
- **复合主键**：元组比较 `(a, b) > (?, ?)`（MySQL / PG / SQLite 都支持）；
- **无主键表**：退化为一次性流式搬运，**不可续跑**，报告里明确标注「该表不支持中断续传，中断需整表重来」（与 `docs/08 §4` 的措辞一致）。

为什么不用行号/`LIMIT OFFSET`：偏移分页在并发写入下会跳行或重复，而键集不会。

### 2. 幂等：键集推进天然幂等；从头重跑要求先清空目标表

- 续跑从检查点的键继续，已搬过的键不会再发；
- **不做 upsert**：`INSERT ... ON CONFLICT`（PG/SQLite）与 `ON DUPLICATE KEY`（MySQL）语义不同，跨引擎统一会把「覆盖」和「跳过」混在一起；
- 从头重跑（没有检查点）时遇到主键冲突就报错，并在错误里说明「目标表已有数据，请先清空或改用续跑」。

### 3. 校验：行数 + 全量哈希（按主键排序）

搬运过程中对源行做流式哈希；搬完再对目标端按同样顺序读一遍、算同一个哈希并比对。

- 规范化：所有值转成文本后按列拼接（NULL 用固定哨兵 `\x00NULL`），避免 `1` 与 `'1'` 被判成不同；
- **必须按主键排序**：跨引擎的物理顺序不可比，不排序的哈希没有意义；无主键表因此**只做行数校验**，并在报告里标注「未做内容校验」；
- 代价：大表要二次扫描（源一次、目标一次）。这是「能不能发现丢数据」与「多读一遍」的取舍，选前者。

### 4. 内存：流式游标 + 每批 1000 行多行 INSERT

每批在目标端发一条 `INSERT INTO t (cols) VALUES (...), (...), ...`，内存上限约为 `批大小 × 行宽`。批大小可配，默认 1000（与批量修改的分批粒度一致）。

## 后果

**正面**

- 中断可续、可验证，且内存不随表大小增长。
- 三条口径都能在真机上用现有 `bulk_exec` 的分批经验验证。

**负面 / 必须说清**

- 无主键表既不支持续跑也不做内容校验——这两个限制必须在报告里出声，不能只写在文档里。
- 从头重跑要先清空目标表，属于「已知的麻烦」，不做自动清理（自动清理等于替用户删数据）。
- 哈希是**行级内容**哈希，不覆盖索引、外键、统计信息——结构正确性由前面的 DDL 步骤保证。

## 验证计划（实现时按这个写）

1. 2 万行搬到一半注入失败 → 续跑 → 目标行数与源一致、无重复主键、哈希一致。
2. 手工改目标里 1 行 → 哈希校验必须报出不一致（并指出表名）。
3. 无主键表：报告里必须出现「不可续跑 / 未做内容校验」标记。
4. 并发写入下重复跑：从头重跑应因主键冲突被拒，而不是静默跳过。

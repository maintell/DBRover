# ADR-0004 · 环境类型作为独立安全维度，确认强度分级化

- 状态：**已采纳**
- 日期：2026-11-02
- 影响面：`model.Connection`、`service/change`、`service/query`、`agent/policy`、UI、审计

---

## 背景

模型澄清需求：**能否区分环境（测试/生产），并让不同环境的确认强度不同——测试库改数据不打扰，生产库改数据要确认。**

原设计只有两个维度：

- `access_mode`：`read-only` / `read-write` / `admin`
- `Risk Level`：`R0`–`R4`

这两个维度都不表达「这是哪个环境」。后果很具体：

1. **默认只读对测试库是纯负担。** 开发改一条测试数据要先切模式，人会长期把连接设成 `read-write` 图省事。
2. **风险分级对测试库是纯噪音。** 测试库上 `DROP TABLE` 弹「输入表名确认」，用户两天后就形成肌肉记忆，在生产上照样无脑确认。
3. **`admin` + 生产 = 无保护。** 只要有人把生产连接设成读写，所有保护都失去意义，因为没有任何机制知道它是生产。

第二个问题是更本质的：**二元「二次确认」本身就是坏设计**。它把「改 1 行」和「DROP 一张 12 万行的表」都归为「弹个框」，结果必然是用户学会忽略弹框。

---

## 决策

### 1. `Environment` 是一等字段，与 `access_mode` 正交

```go
type Environment string
const (
    EnvLocal      Environment = "local"       // 本机 / 内存 / 临时库
    EnvTest       Environment = "test"        // 测试、开发、CI
    EnvStaging    Environment = "staging"     // 预发、UAT、灰度
    EnvProduction Environment = "production"  // 生产
    EnvUnknown    Environment = "unknown"     // 未声明（默认）
)
```

**正交性**：环境描述「这是什么库」，访问模式描述「允许做到什么程度」。四种组合都合法，但严格度取两者中最严的一侧。

| 组合 | 合法 | 说明 |
|---|:--:|---|
| 生产 + 只读 | ✅ | 最常见的默认 |
| 生产 + 读写 | ✅ | 需要，但受最高摩擦约束 |
| 测试 + 只读 | ✅ | 排查时用 |
| 测试 + 读写 | ✅ | 开发日常 |
| 生产 + `admin` | ⚠️ | 允许，但等价于「无兜底」，UI 强警示 |

### 2. 严格度顺序与 `unknown` 的定位

```
local(0) < test(1) < staging(2) < production(3) = unknown(3)
```

**`unknown` 按 `production` 处理。** 新连接一律从 `unknown` 开始。

理由：任何「默认猜成测试」的设计都会在误判时造成事故；而「默认当成生产」的代价只是多点一次确认。**默认值的代价必须落在「麻烦」一侧，不能落在「事故」一侧。**

### 3. 放宽必须显式声明，收紧可以自动推断

这是本 ADR 最重要的一条规则：

| 方向 | 允许自动？ | 理由 |
|---|:--:|---|
| **收紧**（test → production） | ✅ 自动，并提示用户确认 | 误收紧的代价是多点一次；漏收紧的代价是事故 |
| **放宽**（production → test） | ❌ 必须人工显式操作 | 放宽是放弃保护，只能由人承担责任 |

推论：

- 自动检测（主机名、库名、服务器身份）**只能提升严格度，永不降低**。
- 从 `unknown` 降到 `test` 需要用户勾选「我确认这是非生产库」，并写入审计。
- 团队模式下，放宽权限归管理员，普通成员不可改。

### 4. 用「摩擦分级」取代二元确认

```
F0  静默         无打扰，仅落审计
F1  内联预览     变更集/预案面板展示将执行的语句，点「提交」即视为确认
F2  弹窗确认     展示 SQL + 影响行数 + 回滚语句
F3  输入确认     必须键入对象名（表名/库名）
F4  输入 + 冷却  键入正确 + 按钮 3 秒后才可点
F5  阻断         策略拒绝，需改连接配置或走审批流程
```

**F1 是关键设计**：让「确认」变成「看见将要执行什么」，而不是「点掉一个对话框」。人对「看见 SQL」的注意力远高于「点确定」。

### 5. 策略矩阵

| 环境 \ 风险 | `R0` 只读 | `R1` 单行写 | `R2` 批量写 | `R3` DDL | `R4` 破坏性 |
|---|:--:|:--:|:--:|:--:|:--:|
| `local` | F0 | F0 | F0 | F1 | F2 |
| `test` | F0 | F0 | F1 | F2 | F3 |
| `staging` | F0 | F1 | F2 | F3 | F3 |
| `production` | F0 | F1 | F2 | F3 | F4 |
| `unknown` | 同 `production` | | | | |

**这直接回答了「测试环境不需要二次确认」**：测试库上 `R0`–`R2` 全部 F0/F1，不打断；只有 `R3`/`R4` 才有一层轻确认（因为 DDL 在测试库上也可能毁掉别人的测试数据）。

### 6. 路径与规模的修正规则

基准值之上叠加，取最大值（封顶 F4）：

| 条件 | 修正 |
|---|---|
| 变更集路径（自带预览） | −1，但 `production` 上不低于 F1 |
| 脚本含 > 5 条语句 | +1 |
| 影响行数 > 10000 | +1 |
| 影响行数为 `unknown`（无法估算） | +1 |
| 目标表 7 天内无备份记录 | +1 |
| 命中只读连接 | 直接 F5 |
| 团队模式下的只读角色 | 直接 F5 |

### 7. 服务器身份常驻显示

**光有环境标注意味着依赖人的正确性。需要一层不依赖人的校验。**

每次连接后取真实服务器身份并在界面常驻显示：

| 引擎 | 身份来源 |
|---|---|
| PG | `inet_server_addr()` + `pg_postmaster_start_time()` + `version()` |
| MySQL | `@@hostname` + `@@server_uuid` + `@@version` |
| MSSQL | `SERVERPROPERTY('ServerName')` + `SERVERPROPERTY('InstanceName')` |
| Oracle | `v$instance.host_name` + `v$instance.instance_name` + `db_unique_name` |
| SQLite | 文件绝对路径 + `PRAGMA page_count` |
| Redis | `INFO server` 的 `run_id` |
| Mongo | `hello.setName` + `hostInfo.system.hostname` |
| ES | `_cluster/health` 的 `cluster_uuid` + `_nodes` 的主机名 |

用途：

1. 界面上永远显示**真实主机名与实例标识**，而不只是连接别名。改连接别名骗不过去。
2. 同一连接串连到了不同实例（身份指纹变化）→ 提示「目标服务器已变更」，并要求重新确认环境。
3. 环境声明卡片里同时展示「声明值」与「检测建议值」，不一致时高亮。

### 8. 环境对其它模块的影响

| 方面 | `local` / `test` | `staging` | `production` |
|---|---|---|---|
| 新连接默认 `access_mode` | `read-write` | `read-only` | `read-only` |
| Agent 权限上限 | `autonomous` | `write-with-approval` | `write-with-approval` |
| 单事务批量阈值 | 5000 行 | 2000 行 | 500 行 |
| 回滚语句 | 可选 | 必须生成 | 必须生成；不可生成则 +1 摩擦 |
| 结果集快照 | 允许 | 需显式同意 | 禁止 |
| 作为**迁移目标** | 允许 | 允许 | **默认禁止**，需 R4 双确认并输入库名 |
| 审计 | 记录 | 记录 | 记录 + 建议定期外部导出 |
| UI 标识 | 灰/绿 | 黄 | 红 + 标签页与结果区常驻标识 |
| Agent 可自主发起 DDL | 允许（`autonomous`） | 否 | **否，一律人工审批** |

## 理由

### 为什么不用「环境 = 连接分组」

分组是视觉概念，可随时改名、可多分组。环境是安全属性，必须唯一、必须不可含糊、必须参与策略计算。混在一起会导致「这个连接在两个组里，它到底算不算生产」。

### 为什么 `unknown` 不猜

产品最常见的失败模式是「聪明地猜错」。测试库和生产库的命名没有通用规律，云上实例的域名更是无语义。猜对的收益（少点一次确认）远小于猜错的代价（在生产上无确认地 `DROP TABLE`）。

### 为什么摩擦要分级而不是加强确认文案

加粗字体、红色背景、二次弹窗都会被适应。**只有「提高操作成本」和「展示真实后果」两个手段长期有效**。F3（输入表名）提高了成本，F2（展示 SQL 与影响行数）展示了后果，F4（冷却）打断了肌肉记忆。

### 为什么不把「环境」做成风险分级的修正项

风险分级描述的是**语句本身的危险性**（客观），环境描述的是**发生位置的代价**（上下文）。前者可以在离线分析，后者必须来自连接配置。把环境塞进风险分级会让 `RiskGrade(sql)` 需要连接参数，破坏其纯函数性质与可测试性。

保持正交、在执行门处合成，是更清晰的分层。

## 后果

**正面**

- 测试库日常操作零打扰，生产库有真实阻力，摩擦与代价匹配。
- 环境误判有兜底（`unknown` → 生产；身份指纹变化 → 重新确认）。
- 确认行为可被测试：策略矩阵是纯函数，可穷举断例。
- 为团队模式提供权限基线（环境决定默认值，角色决定上限）。

**负面 / 需要承担**

- 新连接必须先声明环境，多一步（可用「批量声明」缓解）。
- 环境检测的启发式一定会有误报，需要「我确认这是非生产库」的逃逸阀与审计。
- 策略矩阵需要持续维护：新增风险等级或调整阈值会影响所有引擎。
- 服务器身份采集每个引擎都要写，且部分引擎需要额外权限（如 Oracle `v$instance`）。

**约束（必须持续遵守）**

- 禁止任何「自动放宽环境」的代码路径。
- 禁止把环境判断写成 `if conn.Name contains "prod"`——必须走 `Connection.Environment`。
- 新增引擎时必须实现 `ServerIdentity()`；缺失视为能力不完整。
- 摩擦等级的计算必须是纯函数 `Friction(env, risk, modifiers) → level`，可单测穷举。

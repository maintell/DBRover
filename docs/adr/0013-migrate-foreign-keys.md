# ADR-0013 · 迁移外键：目标库已有被引用表才建，否则跳过并点名

- 状态：**已采纳（部分实现）**
- 日期：2026-11-05
- 影响面：`internal/service/migrate.go`（`BuildMigrationForeignKeyDDL`）、`cmd/dbrover`、`docs/08 §4`

---

## 背景

外键是迁移里唯一需要「跨表」的信息。三种典型场景互相冲突：

1. **整库迁移**：父表与子表都在集合里，只是顺序要排对；
2. **只迁一张子表**：被引用的父表不在本次迁移里——但目标库可能本来就有；
3. **被引用的表根本不存在**：建外键必然失败。

三种情况不能用同一条规则处理。若一律「有外键就阻断」，场景 2 会变得不可用；
若一律「跳过外键」，场景 1 会在用户不知情时丢掉引用完整性——那是数据正确性问题。

## 决策

**在数据搬完之后，按「目标库里此刻是否已有被引用表」逐条决定：有则建，无则跳过并点名。**

- 检查对象是**目标库**，不是「本次迁移集合」：这正好让「先迁父表、再迁子表」自然工作；
- 引擎不支持 `ALTER TABLE ADD FOREIGN KEY`（SQLite）→ 全部跳过，理由写明；
- 约束名用确定性的 `fk_<表>_<列...>`（复用 `defaultFKName`），不沿用源名——MySQL 的
  外键名要求库内唯一，沿用源名在跨库合并时容易撞；
- 动作子句（`ON DELETE` / `ON UPDATE`）原样带上：它是语义的一部分，不能悄悄丢掉；
- 跳过的外键进 `BuildMigrationNotes`，迁移报告里逐条列出「外键 X 未建：目标库没有表 Y」。

## 后果

**正面**

- 整库迁移能拿到完整的外键；单表迁移不会被一条外键卡死，但缺口是明确可见的。
- 「先迁父表再迁子表」成为可操作的步骤，而不是需要用户去猜的顺序。

**负面 / 必须说清**

- 迁移完成**不等于**引用完整性完成：跳过的外键要人工补，报告会说。
- 循环依赖（A 引用 B、B 引用 A）需要两轮：第一轮会在某一侧跳过，补建即可。
- 不做延迟约束（`DEFERRABLE`）——PG 支持但 MySQL 5.7 不支持，统一不做。

## 验证计划

1. 被引用表在目标库存在 → 生成 `ALTER TABLE ... ADD CONSTRAINT fk_... FOREIGN KEY ...`，动作子句在。
2. 被引用表不在目标库 → 不生成语句，`skipped` 里点名「目标库没有表 X」。
3. 目标引擎不支持加外键（SQLite）→ 全部跳过，理由写明「该引擎不支持 ALTER TABLE ADD FOREIGN KEY」。
4. 真实实例（MySQL → PG）：父表先迁、子表后迁，外键建出来；把父表删掉再迁子表，外键被跳过且报告可见。

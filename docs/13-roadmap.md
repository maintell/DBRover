# 13 · 路线图

> 排序原则：**先打通最容易被低估的抽象，再叠加差异化能力。** 不是「先做简单的」。

---

## 1. 排序逻辑

大多数数据库工具项目会这样失败：先做一个引擎做到 90%，然后发现抽象是错的，第二个引擎要重写一半。

所以里程碑的划分标准不是「功能多少」，而是**每次尝试证伪一个假设**：

| 里程碑 | 要证伪的假设 | 如果失败了 |
|---|---|---|
| M1 | 「一套 Connector 抽象能同时容纳 PG / MySQL / MSSQL」 | 抽象要重做，越早发现越好 |
| M2 | 「变更安全（plan + 回滚 + 审批）是可行的产品形态」 | 差异化不成立，需要重新定位 |
| M3 | 「Agent 能稳定完成真实任务且不越权」 | 差异化不成立，退回「AI 辅助」 |
| M4 | 「剩余 5 种引擎能低成本接入」 | 抽象仍不足，或需分级支持 |
| M5 | 「备份/迁移的自研实现质量可接受」 | 退回「调用原生工具 + 明确边界」 |

**已知的下一步（按性价比排序）**

1. Redis 连接器：模型已由 ADR-0007 定好，需引入 `go-redis`（纯 Go）。**先确认依赖再动手**。
2. SQL Server 连接器：磁盘已够（需拉 ~1.5G 镜像），难点是 `sys.*` 自拼 DDL。
3. `docs/07` 验收 12 手写 SQL 模式：需要 DDL 解析，工作量大于本轮任何一项。
4. AI Agent：等「接哪个模型服务」这个决策。

## 2. 里程碑

### M0 · 文档基线（当前）

**产出**：本套文档 + ADR-0001/0002/0003。

**门禁**：能回答「新增一个引擎要改哪些文件」「Agent 的写操作被谁拦住」「MySQL 上 DDL 的回滚是什么语义」这三个问题。

---

### M1 · 最小闭环（PG + MySQL + MSSQL）

**目标**：证明抽象成立。**只做只读，不做写入。**

| 范围 | 内容 |
|---|---|
| 连接 | 3 引擎连接/测试/健康检查；SSH 单跳隧道；凭据存 OS keychain；只读模式；**环境声明 + 服务器身份采集与显示** |
| 元数据 | 四层树、对象详情、DDL 查看（含 MSSQL 自拼）、对象搜索 |
| 查询 | 编辑器（Monaco）+ 执行 + 结果网格 + keyset 分页 + 取消 |
| 基础设施 | loopback 服务 + token、SQLite 元数据库、审计基础表、OpenAPI 契约、WS 事件 |
| 体验 | 工作区持久化、查询历史、收藏、快捷键 |

**刻意不做**：写入、DDL、AI、监控、备份、NoSQL、团队模式。

**为什么包含 MSSQL 而不只做 PG+MySQL**：MSSQL 是「同族但不相似」的最佳试金石——无原生 DDL、分页语法不同、需要 XML 计划解析、有 `IDENTITY`/计算列/时态表。它能把抽象里的漏洞逼出来。如果 M1 只做 PG+MySQL，两者都是「schema 分层清晰、有 LIMIT」，抽象很容易看起来很美。

**门禁（全部满足才进 M2）**

1. 3 引擎通过 `drivertest` 的 `connect` / `metadata` / `query` / `pagination` / `split` 套件。
2. 类型保真测试全绿（每种引擎一张全类型表）。
3. 5000 表库元数据树展开 < 1.5s（P95）。
4. 100 万行结果翻页不 OOM。
5. 取消在 1s 内生效（引擎侧验证）。
6. 代码中无 `switch engine`（用 `Capabilities()`）。
7. OpenAPI 契约评审通过，前端零手写 fetch。
8. 8 引擎（本里程碑内 3 个）的服务器身份采集可用，且身份变化能阻断。

**风险**：MSSQL 的 DDL 自拼工作量会超预期 → 允许 M1 里 MSSQL 的「查看 DDL」标为已知限制，但**必须在 M4 前补齐**（有对应测试）。

---

### M2 · 写入与变更安全

**目标**：验证差异化成立。这是产品从「查询工具」变成「管理工具」的分界。

| 范围 | 内容 |
|---|---|
| 数据编辑 | 网格编辑、变更集、乐观并发、提交预览、回滚、批量修改 |
| 变更预案 | Change Plan（DDL + DML）、影响评估、回滚生成、风险分级、审批 |
| 结构管理 | 表设计器（3 引擎）、索引管理、视图管理 |
| 安全 | 只读守卫（双层）、审计链、审批哈希绑定、危险操作门槛、**摩擦分级 F0–F5（环境 × 风险）** |
| 体验 | 事务面板、生产连接标识 |

**门禁**

1. 风险分级器对 40 条边界 SQL 的判定全部符合预期（含 `WHERE 1=1`、注释混淆、CTE 写）。
2. 只读连接上所有写路径被拒（引擎层或分析层），有测试。
3. 乐观并发冲突不会覆盖数据。
4. 审批 A 执行 B 被拒。
5. 审计链篡改可检测。
6. MySQL 上 DDL 回滚显示「丢数据」警示。
7. **用一个真实的中等规模库（≥50 张表）完整走一遍「加字段 + 改数据 + 回滚」，无事故。**
8. 摩擦矩阵（5 环境 × 5 风险 × 修正项）穷举单测全绿；测试库上 `R0`–`R2` 实测无弹窗打断。

**风险**：风险分级器的解析器工作量可能被低估 → 允许 v1 用「保守判定」（解析失败即 R4），但必须记录保守率指标，过高（>30%）说明解析器不足。

### M3 · AI Agent

**目标**：验证「Agent 能稳定完成任务且不越权」。

**前置**：M2 的权限与审批完备。Agent 建立在安全机制之上，不是反过来。

| 范围 | 内容 |
|---|---|
| 运行时 | 14 个工具、执行循环、预算与循环检测、多 provider（OpenAI 兼容 + Ollama） |
| 上下文 | 分层注入、schema 检索（名称 + 注释 + FTS）、结果摘要、长会话压缩 |
| 安全 | 三模式权限、审批流、提示注入防御、审计 |
| UI | 步骤时间线、可展开 SQL、审批卡片、结论可溯源 |
| 质量 | 评测集（3 引擎各 10 条 + 注入用例 3 条）、CI 门禁 |

**门禁**

1. 评测集：只读分析类一次通过率 ≥ 70%。
2. **不安全行为率 = 0**（CI 阻断）。
3. 提示注入用例全部未能诱导执行。
4. 2000 表库上下文构建 < 1s，token < 3k。
5. 不注入全量 schema（代码检查）。
6. 会话可完整重放。
7. 真实试用：3 名工程师用 1 周，记录「Agent 完成了什么 / 卡在哪」。

**风险**：模型能力波动导致通过率不稳 → 评测集按 provider 分别记录基线，不追求跨模型一致。

### M4 · 引擎补齐与对象管理

| 范围 | 内容 |
|---|---|
| 引擎 | Oracle（go-ora）、SQLite、Redis、MongoDB、Elasticsearch |
| 能力 | 各引擎的降级路径与专属视图（Redis 命令模式、Mongo 文档树、ES 命中列表） |
| 对象 | 例程、序列、类型、触发器管理 |
| 工具 | 结构比对、依赖检查 |
| 补齐 | MSSQL 的 DDL 自拼（M1 遗留） |

**门禁**

1. 8 引擎全部通过 `drivertest` 基础套件。
2. 每种引擎至少 1 条端到端场景验证（见 PRD §4）。
3. Oracle 许可约束落地：AWR 未授权时静默降级已验证。
4. MSSQL / SQLite 的 DDL 往返测试全绿。
5. 降级策略表（04 文档 §7）逐条有对应实现与提示。

**风险**：Oracle 驱动兼容性 → 做 go-ora / godror 双实现的 POC，按结果定；若 go-ora 不满足则接受 CGO 并调整发布策略（记 ADR）。

### M5 · 备份、迁移与监控

| 范围 | 内容 |
|---|---|
| 备份 | DBR 格式、压缩/加密、断点续跑、产物浏览、计划任务 |
| 恢复 | 安全约束、恢复后校验、演练报告 |

**门禁**

1. 备份强杀进程后续跑成功，数据完整。

4. 监控首屏 2s 内出结论，采集全部带超时。

**风险**：自研导出的格式兼容性 → 容器格式带 `format_version`，并提供 `dbrover backup migrate` 升级工具。

## 5. 风险登记册

| # | 风险 | 影响 | 概率 | 缓解 |
|---|---|:--:|:--:|---|
| R1 | Connector 抽象不足以容纳 8 引擎 | 高 | **已发生并部分缓解** | 关系型三引擎（SQLite/MySQL/PG）已验证抽象够用；**非关系型确实套不进去**，已在 ADR-0007 里拆成独立的 `KVConnector` 族。剩余风险是 Mongo/ES 是否需要第三代接口 |
| R2 | MSSQL/SQLite 的 DDL 自拼不保真 | 中 | 高 | 往返测试作为门禁；允许标注「生成 DDL 可能与原定义有差异」 |
| R3 | Oracle 纯 Go 驱动不满足需求 | 中 | 中 | 双实现 + build tag；必要时接受 CGO 并改发布策略 |
| R4 | 风险分级器误判率高 | 高 | 中 | 保守优先；监控保守率；提供白名单 |
| R5 | Agent 在真实任务上通过率不达标 | 高 | 中 | M3 早期做 spike；不达标则降级为「AI 辅助」定位 |
| R6 | 自研备份/迁移的数据正确性缺陷 | 高 | 中 | 三重校验；不允许「校验未通过」被忽略；强制演练 |
| R7 | 大库性能（元数据、结果集） | 中 | 中 | 按需加载 + 缓存 + 游标；M1 门禁含 5000 表与 100 万行 |
| R8 | 范围蔓延导致 M1 无限延长 | 高 | 高 | M1 明确「不做清单」；门禁未达不进 M2 |
| R9 | 提示注入被利用 | 高 | 低 | 四层防御 + 评测硬门禁；写操作强制人工审批 |
| R10 | 单机 SQLite 元数据库损坏 | 中 | 低 | WAL + 定期 `VACUUM INTO` 备份；损坏时允许重建（审计除外） |
| R11 | `KVConnector` 只有设计没有实现 | 中 | 中 | ADR-0007 是纸面结论，没有实现过。接 Redis 时先做只读三件套（`Scan`/`Inspect`/`Value`）验证接口站得住，再加写路径；接口若需改，早改代价小 |

## 7. 每个里程碑的「完成定义」

统一口径，避免「差不多完成」：

1. 对应需求编号全部有实现或明确的「不实现 + 理由」。
2. 门禁项全部通过，且有可复现的验证记录（不是「我试过」）。
3. 文档已回填（实现与文档不一致视为未完成）。
4. 无新增 TODO；延后项写入「已知限制」。
5. 新增/修改的连接器通过 `drivertest`。
6. 破坏性设计变更已落 ADR。

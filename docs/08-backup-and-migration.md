# 08 · 备份、恢复与迁移

> 需求编号：`FR-BAK-01..05`、`FR-MIG-01..06`。核心命题：**备份的价值只在恢复成功那一刻兑现；迁移的价值只在数据一致那一刻兑现。**

---

## 1. 为什么自实现导出

不 shell 调用 `pg_dump` / `mysqldump` / `mongodump` / `expdp`。

| 理由 | 说明 |
|---|---|
| 跨平台分发 | 用户机器上不一定有目标版本的客户端工具 |
| 版本耦合 | 客户端版本必须 ≥ 服务端，用户环境不可控 |
| 无进度 | 外部进程难给出细粒度进度、断点、取消语义 |
| 无法服务化 | 容器里不带这些工具，团队模式会崩 |
| 无法加密/压缩 | 需要额外的管道与临时文件 |
| 安全面 | 通过环境变量传密码、命令行可见凭据 |

代价是要自己实现各引擎的读取与写出，以及格式版本兼容。这个代价是值得的，且可在 `drivertest` 中覆盖。

## 2. 备份

### 2.1 备份类型

| 类型 | 内容 | 用途 |
|---|---|---|
| `schema` | 仅结构（DDL） | 建空库、结构比对 |
| `data` | 仅数据 | 已有结构上灌数据 |
| `full` | 结构 + 数据 | 完整备份（默认） |
| `table` | 指定表的结构与数据 | 局部备份/迁移演练 |

**不做物理备份**（如 `pg_basebackup`、`XtraBackup`）：物理备份与版本、平台、文件布局强耦合，且需要停机或复制槽管理，超出本产品定位。在 UI 中说明「本产品做逻辑备份；物理备份请用引擎原生工具」，并给出对应命令。

### 2.2 一致性模型（必须让用户选择）

| 模式 | 实现 | 优点 | 缺点 |
|---|---|---|---|
| `snapshot`（默认，≤ 50GB） | 全程持一个只读事务/一致性快照 | 跨表一致，可放心恢复 | 长事务：阻碍 vacuum（PG）、占用 UNDO（Oracle）、阻塞 DDL |
| `per-table` | 每表独立读取，不持全局事务 | 无长事务副作用 | 跨表可能不一致（表 A 读到新数据、表 B 读到旧数据） |
| `quiesce` | 要求无写入（检测活跃事务） | 一致且短 | 需业务配合 |

默认策略：预估体积 ≤ 50GB 用 `snapshot`；超过则**强制提示**并让用户在三者中选择，默认 `per-table` 且显示黄色警告。

预估体积来自 `ObjectStats` 汇总；不准时以「未知」处理，交给用户选。

### 2.3 容器格式（`DBR`）

单文件容器，便于传输与校验。

```
┌─ Header ─────────────────────────────────┐
│ magic  "DBROVER\x00"          8 bytes    │
│ format_version  uint16                   │
│ flags           uint16  (bit0=encrypted, │
│                          bit1=compressed)│
│ header_len      uint32                   │
│ header_json     [header_len]             │
└──────────────────────────────────────────┘
┌─ Sections（顺序写，可并行解压）─────────┐
│ manifest.json      元信息、对象清单       │
│ schema.sql         结构（可选）           │
│ data/<table_id>    行数据分块             │
│ checksums.json     每节 sha256            │
└──────────────────────────────────────────┘
```

`manifest.json`：

```json
{
  "created_at": "2026-11-02T10:00:00Z",
  "engine": "mysql",
  "server_version": "8.0.36",
  "database": "shop",
  "mode": "snapshot",
  "encrypted": true,
  "compression": "zstd",
  "objects": [
    {"kind":"table","name":"order","rows":120345,"est":true,
     "data_section":"data/t_3f2a","schema_section":"schema.sql#order"}
  ],
  "tool_version": "0.1.0"
}
```

**行数据编码**：按表分块，每块 ≤ 8MB。块内为长度前缀的行记录（列值按 `model.ColumnType` 编码）：

- 定长整数/浮点：小端定长
- 字符串：`uvarint(len) + utf8`
- `NULL`：长度位 `0xFF` 特殊标记
- `Decimal`：字符串编码（保真优先）
- 二进制：`uvarint(len) + bytes`
- 时间：`int64 unix_nanos` + 时区标记

**不用 CSV 作为内部格式**：CSV 无法表达 `NULL` vs `''`、无法保真 `Decimal`、无法表达嵌套类型。

### 2.4 压缩与加密

| 项 | 选择 | 理由 |
|---|---|---|
| 压缩 | `klauspost/compress/zstd` | 纯 Go、压缩比与速度均衡、可流式 |
| 加密 | `filippo.io/age`（X25519 + ChaCha20-Poly1305） | 纯 Go、现代、支持口令与公钥两种模式 |
| 口令派生 | `argon2id` | 抗暴力破解 |

加密为**可选**，默认关闭（本地磁盘备份，加密会增加恢复门槛）。涉及跨机器传输时 UI 强烈建议开启并给出说明。

### 2.5 备份流程

```
1. 预检
   · 连接可用、权限足够（读所有目标对象）
   · 磁盘剩余空间 ≥ 预估体积 × 1.2
   · 目标路径可写
2. 建立一致性上下文（按模式）
3. 写 Header + manifest（先占位，结束时回填行数）
4. 逐对象导出：schema → data（分块，落检查点）
5. 计算并写 checksums
6. 回填 manifest，落最终索引
7. 校验：重新打开容器，抽样读块并比对 checksum
```

**断点续跑**：每完成一个对象（或对象的每 N 块）写 `checkpoint.json`（同目录旁挂），恢复时跳过已完成部分。容器中断时标记为 `incomplete`，恢复成功后改写。

### 2.6 备份产物浏览（`FR-BAK-03`）

不解压全量即可预览：

- 读取 Header + manifest → 列出对象、行数、结构。
- 按需解压单个 section 查看结构或样本行（前 100 行）。
- 这让「这个备份里到底有什么」变成一个秒级问题。

### 2.7 备份计划（`FR-BAK-02`）

- Cron 表达式 + 时区（默认本地时区，显式显示）。
- 保留策略：保留 N 份 / 保留 N 天（按数量与时间取交集）。
- 失败重试：2 次，间隔 5 分钟。
- 通知：本地通知（桌面）/ 退出码（无头）。
- 计划任务在桌面模式下由内置调度器执行；应用未运行时**不执行**（不做后台服务，避免用户不知情）。UI 明确说明这一点。

## 3. 恢复

### 3.1 安全约束（硬性）

1. **目标必须是新库/新 schema 或空 schema**。检测到目标已有同名对象 → 拒绝，除非用户勾选「允许覆盖」并输入目标库名（`R4` 流程）。
2. **禁止恢复到源连接的同名库**（备份文件里的源信息与目标匹配时直接阻断）。✅ v1 已做：容器头记 `source_id`（sqlite 为绝对路径、网络引擎为 `host:port/库名`，由调用方提供），恢复时与目标身份一致即拒绝（`TestRestoreRefusesSource`）。注意这只是「防手滑」——身份串由调用方给，不是认证。
3. 恢复前展示：将创建的对象数、将插入的预估行数、所需空间。
4. 恢复在**单事务**内进行（若引擎支持 DDL 事务），失败整体回滚。

### 3.2 流程

```
1. 打开容器，校验 header 与 checksums
2. 版本与引擎兼容性检查
   · 同引擎：主版本差 ≤ 1 允许，否则警告
   · 跨引擎：转交迁移模块（见 §4）
3. 目标校验（空/新建/允许覆盖）
4. 可选：关闭外键检查（按引擎），恢复后重建并校验
5. 建结构 → 灌数据（分批，进度可见）
6. 重建索引与外键（PG/MySQL 上先灌数据再建索引更快）
7. 更新统计信息（`ANALYZE`）
8. 校验（见 §3.3）
```

### 3.3 恢复后校验（`FR-BAK-05`）

| 检查 | 方法 | 失败处理 |
|---|---|---|
| 对象数一致 | 比对 manifest 与目标元数据 | 阻断，报告缺失对象 |
| 行数一致 | 逐表 `COUNT(*)` 比对（大表用统计估算 + 抽样精确） | 报告差异 |
| 内容校验 | 抽样 1000 行，按主键比对哈希 | 报告差异行 |
| 索引有效 | 查询系统表确认索引 `valid` | 报告并建议 `REINDEX` |
| 外键一致 | 校验约束已 `VALIDATED` | 报告 |

输出**演练报告**（可导出 Markdown）：时间、耗时、对象与行数、差异项、结论（通过/带警告/失败）。

> 这个报告就是「备份到底有没有用」的答案，是本模块对用户最直接的价值。

## 4. 迁移

### 4.1 适用范围

- 同引擎跨实例（版本升级、机房搬迁）
- 跨引擎（MySQL → PostgreSQL 等）
- 同实例跨 schema（分库拆分）

**不适用**：持续同步、增量 CDC 常驻。文档与 UI 都要写清。

### 4.2 流程

```
1. 选择源连接 + 对象；选择目标连接 + 目标库
2. 类型映射（自动 + 人工覆盖）
3. 预检报告
4. 结构生成与审阅（走 Change Plan）
5. 建结构
6. 数据搬运（分批、可暂停、可续跑、幂等）
7. 校验（行数 + 校验和 + 抽样）
8. 收尾（索引、外键、统计信息）
9. 迁移报告
```

### 4.3 类型映射

映射表以**中立类型为中介**，但**优先使用原始类型**：

```
source.Raw  →[source.ToNeutral]→  neutral  →[target.FromNeutral]→  target DDL type
                     ↓
              若 neutral 有损（如 MySQL TEXT 无长度）→ 标记冲突，要求人工
```

关键映射（节选）：

| 源 | 目标 | 映射 | 冲突/注意 |
|---|---|---|---|
| MySQL `TINYINT(1)` | PG | `boolean` | 可能是数值而非布尔 → **必须人工确认** |
| MySQL `DATETIME` | PG | `timestamp`（无时区） | 不要映射成 `timestamptz`（会引入时区偏移） |
| MySQL `TIMESTAMP` | PG | `timestamptz` | MySQL `TIMESTAMP` 有 2038 上限 |
| MySQL `UNSIGNED BIGINT` | PG | `numeric(20)` | PG 无无符号；用 `bigint` 会溢出 |
| MySQL `ENUM` | PG | 原生 `enum` 类型 或 `text + CHECK` | 原生 enum 增减值需 `ALTER TYPE`，建议 `text+CHECK` |
| MySQL `SET` | PG | `text[]` + CHECK | 无直接对应 |
| PG `jsonb` | MySQL | `JSON` | 保真但查询能力不同 |
| PG `uuid` | MySQL | `char(36)` | 索引体积变大；或 `binary(16)` 需转换逻辑 |
| PG `array` | 任意 | 无直接对应 → 建议子表或 JSON | **冲突** |
| Oracle `NUMBER` | PG | `numeric(p,s)`；无精度时 `numeric` | Oracle 的 `NUMBER` 无精度是浮点语义 |
| Oracle `VARCHAR2(n)` | PG | `varchar(n)` | 注意 `n` 是**字节**还是字符（`CHAR` 语义） |
| Oracle `CLOB` | PG | `text` | — |
| Oracle `DATE` | PG | `timestamp` | **Oracle DATE 含时间**，不能映射为 `date` |
| MSSQL `NVARCHAR` | PG | `varchar` | 长度按字符计 |
| MSSQL `DATETIME2` | PG | `timestamp` | — |
| MSSQL `UNIQUEIDENTIFIER` | PG | `uuid` | — |
| SQLite 任意 | 任意 | 按亲和性推断 + 抽样确认 | SQLite 类型弱，需看实际值 |
| 任意 → SQLite | — | 按亲和性收敛 | 精度、时区、`boolean` 均退化 |

**规则**

1. 逢「有损」「语义漂移」「无直接对应」→ 标为**冲突**，逐项要求人工决策，不可自动放行。
2. 冲突项必须展示：源类型、建议目标类型、损失说明、备选方案。
3. 精度损失（`decimal(65,30)` → `decimal(38,10)`）必须预检实际最大值。

### 4.4 预检清单（`FR-MIG-03`）

| 检查 | 方法 | 阻断级别 |
|---|---|---|
| 字符集与排序规则 | 比对源/目标 | 警告（可能影响唯一性与排序） |
| 超长字符串 | `MAX(LENGTH(col))` vs 目标长度 | 阻断（会截断或报错） |
| 精度溢出 | `MAX(ABS(col))` vs 目标精度 | 阻断 |
| 时区语义 | 源有 `tz`、目标无（或反之） | 警告 + 需选择转换策略 |
| 空串 vs NULL（Oracle） | 统计 `=''` 的行 | **阻断**（Oracle 里 `''` 就是 `NULL`，无法区分） |
| 大小写敏感 | 目标排序规则是否大小写不敏感 | 警告（唯一索引可能冲突） |
| 唯一约束冲突 | 目标上预跑重复检测 | 阻断 |
| 外键顺序 | 拓扑排序 | 自动（失败则报告循环依赖） |
| 自增/序列起始值 | 取源 `MAX(id)` | 自动设置 |
| 保留字冲突 | 对象名/列名是否目标保留字 | 自动加引号 + 提示 |
| 长度上限（标识符） | 各引擎上限不同（Oracle 30/128、PG 63、MySQL 64） | 警告 + 建议改名 |
| 存储引擎差异 | MySQL `MyISAM` 无事务 | 警告 |

### 4.5 数据搬运与幂等（`FR-MIG-04`）

**分批策略**

```go
// 按主键区间推进，不用 OFFSET（源表并发写入会错位）
for each table:
    if has PK:
        last = checkpoint[table].lastKey  // 空则从头
        loop:
            rows = SELECT * FROM t WHERE pk > last ORDER BY pk LIMIT 1000
            if rows empty: break
            writeToTarget(rows)           // 目标侧用 upsert 或 INSERT ... ON CONFLICT DO NOTHING
            last = rows.last.pk
            saveCheckpoint(table, last, hashOf(rows.keys))
    else:
        // 无主键：按全表一次性流式读取，不可续跑，需提前告知
```

**幂等保证**

- 目标侧写入使用 `INSERT ... ON CONFLICT (pk) DO NOTHING`（PG）/ `INSERT IGNORE` 或 `ON DUPLICATE KEY UPDATE`（MySQL）/ `MERGE`（Oracle/MSSQL）。
- 若目标表由本工具创建且用户选择「迁移专用」模式，可先建**无索引无约束**的表，灌完再加 —— 速度提升显著，但失败后需重建。
- 断点记录包含「最后主键 + 该批主键集合哈希」，重启时校验：若目标该批已存在则跳过，否则补写。

**为什么不用 OFFSET**：源表在迁移期间若有并发插入/删除，`OFFSET` 会漏行或重复。按主键游标是唯一可靠方式。

**无主键表**：无法断点续跑，必须在开始前明确提示「该表不支持暂停续传，中断需整表重来」。

### 4.6 校验（`FR-MIG-05`）

三重校验，逐表输出：

1. **行数**：`COUNT(*)` 精确比对（大表可选：源精确 + 目标精确，都跑一次全表扫描，代价可接受）。
2. **校验和**：逐行 `fnv1a64(规范化行字节)` 求和 + 计数。**与顺序无关**，适合比对。
   ```
   checksum = Σ hash(row)  mod 2^64
   ```
   部分引擎可在服务端计算（PG 用 `md5(string_agg)` 代价高，不推荐）→ 统一在客户端流式计算。
3. **抽样内容**：随机 1000 个主键，双向取值比对（能发现「行数对但内容错」）。

**差异处理**：输出差异表清单（表名、源行数、目标行数、校验和差异、样本差异行），支持「仅重迁差异表」。

### 4.7 迁移报告

| 段 | 内容 |
|---|---|
| 概要 | 起止时间、源/目标、对象数、总行数、总耗时、结论 |
| 结构 | 创建的对象、跳过的对象、类型映射决策记录 |
| 数据 | 逐表行数与吞吐、批次重试次数 |
| 校验 | 行数/校验和/抽样结果、差异清单 |
| 遗留 | 未迁移项、需人工处理项、已知差异 |

可导出 Markdown / JSON。

## 5. 验收清单

| # | 项 | 判定 |
|---|---|---|
| 1 | 备份容器可被独立工具（CLI `dbrover backup inspect`）打开并列出对象 | 集成 ✅（v1）：容器格式已按 §2.3 落地（magic + version + flags + header JSON + 每段长度前缀），`dbrover backup inspect <文件>` 能列出对象清单；`TestBackupInspect` 用**测试自己实现的解析**读容器（不复用产器的解析函数，否则「写错了但读得懂」也会通过）。⚠️ v1 的对象条目只有 kind/name，不含行数与大小——它们要等表导完才知道，而头在最前面（见下方 v1 口径） |
| 2 | 备份中途 kill 进程，重启可续跑且不重复 | 集成 ✅ **表级续跑**（[ADR-0009](adr/0009-backup-resume-granularity.md)）：每写完一张表追加检查点到 `<file>.progress`，续跑时截断到最后一条偏移再继续，容器格式不变。`TestBackupResumeAfterFailure`（注入失败→续跑→断言三段且每表只出现一次）、`TestBackupResumeNeedsCheckpoint`（无检查点必须报 `ErrBackupNoCheckpoint` 并说明整库重跑）。**行级续跑明确不做**：需要 v2 分块表，收益不抵复杂度 |
| 3 | 恢复到已有对象的库被拒绝 | 集成 ✅ 默认拒绝并点名冲突对象（`TestRestoreRefusesNonEmptyTarget`）；`-allow-existing` 可显式覆盖。**与目标的差距**：要求里的「输入目标库名」没做，v1 只用一个布尔开关——挡误操作够用，挡不住「看错目标库」 |
| 4 | 恢复后演练报告给出对象数/行数/索引状态 | 集成 ⚠️ **部分**：对象数与行数有（`TestRestoreRoundTrip` 断言 3 对象 / 3 行，且目标库真的能查到数据）；**索引状态与外键校验未做**，报告里没有这两项 |
| 5 | 加密备份用错误口令无法打开且报错明确 | 单测 |
| 6 | 迁移中断后续跑，目标表行数与源一致且无重复 | 集成（2 万行，中途 kill） |
| 7 | 迁移校验能发现篡改的 1 行 | 集成（人为改一行） |
| 8 | MySQL `TINYINT(1)` → PG 被标记为冲突需人工确认 | 单测 |
| 9 | Oracle 空串检测触发阻断 | 单测 |
| 10 | 超长字符串预检阻断 | 集成 |
| 11 | 无主键表迁移前明确提示不可续跑 | 手动 |
| 12 | `Decimal(65,30)` 全量迁移无损 | 类型保真 |

## 6. 取舍

| 决策 | 选择 | 理由 |
|---|---|---|
| 备份实现 | 自实现流式导出 | 见 §1 |
| 一致性默认 | ≤50GB 用快照，超出让用户选 | 长事务副作用必须由用户知情承担 |
| 内部格式 | 自有二进制 | CSV 无法保真 |
| 迁移游标 | 主键区间 | OFFSET 在并发写入下必然错 |
| 校验和 | 与顺序无关的行哈希求和 | 允许并行与乱序写入 |
| 物理备份 | 不做 | 与版本/平台强耦合，超出定位 |
| 后台调度 | 仅应用运行时执行 | 不装静默守护进程 |

---

## 7. v1 已实现口径（比上面窄，差距写清）

§2–§4 是目标形态。当前只落地了**容器与查看**这一小块，其余（续跑、加密、压缩、恢复演练、迁移）都还没做：

| 项 | v1 做法 | 与目标的差距 |
|---|---|---|
| 容器 | `magic "DBROVER\x00"` + `u16 version=1` + `u16 flags=0` + `u32 header_len` + header JSON + 每段 `u32 len` + 该表的 sql 脚本 | 无 manifest 校验和、无分块偏移表 |
| 段内容 | 就是 `Export` 的 `sql` 格式（建表 + INSERT），同引擎可回放 | 跨引擎迁移要类型映射，不在 v1 范围 |
| 查看 | `dbrover backup inspect <文件>`：只读头部、不连库、秒级列出对象 | 对象条目不含行数/大小（头在最前面，行数要等表导完）；不提供「按需解压单段预览」 |
| 加密 / 压缩 | flags 恒 0，读到非 0 直接拒绝（说清「v1 不支持」） | 目标形态要求可加密压缩 |
| 续跑 | 表级：每张表完成即写检查点，`-resume` 截断后续跑；完成后删检查点 | 行级续跑不做（需 v2 分块表）；单表失败要重导整表，这一点在 ADR-0009 里写明 |
| 恢复 | 同引擎、目标非空默认拒绝、禁止恢复到源库（头部记 `source_id`）、全程单事务；报告给对象数与行数 | **未做**：索引/外键状态、跨引擎；`-allow-existing` 只是布尔开关，没有「输入目标库名」那层确认；`source_id` 由调用方给，只能防手滑，不是认证 |
| 迁移 | **没有** | 验收第 6–12 条未做 |

**为什么先做这一块**：它回答的是「这个备份里到底有什么」，不需要一致性快照、不需要恢复目标校验，却能让后面每一步都不盲跑。

使用方式（CLI）：

```powershell
dbrover backup create -db demo.db -env local -out demo.dbr   # 写容器（全部表）
dbrover backup inspect demo.dbr                              # 只读头，列出对象
```

还没有 HTTP 端点与定时计划；容器里的段是脚本，恢复目前要手工取出来回放。

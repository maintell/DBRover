**设计原则**

- **一屏内完成「写—跑—看」**，不弹窗展示结果。
- 结果区高度可拖拽，双击分隔条复位。
- 侧栏与结果区都是「可关的」，让纯阅读场景有最大编辑面积。

## 2. 编辑器行为

### 2.1 执行语义（最容易产生歧义的地方，必须钉死）

| 触发 | 行为 |
|---|---|
| `Ctrl/Cmd + Enter` | 有选区 → 执行选区；无选区 → 执行**光标所在语句**（按 `SplitStatements` 定位） |
| `Ctrl/Cmd + Shift + Enter` | 执行整个脚本（全部语句，按顺序） |
| `F5` | 同 `Ctrl+Enter`（兼容习惯） |
| 右键 → 执行选中 | 同选区 |

**语句定位规则**

1. 用 `dialect.SplitStatements` 得到语句边界（含起始/结束偏移）。
2. 光标落在某语句的 `[start, end]` 内 → 该语句。
3. 光标在两条语句之间（空白处）→ 取**前一条**。
4. 脚本末尾光标在最后一条之后 → 取**最后一条**。

**多语句执行的错误语义**

- 默认 `stop_on_error = true`：遇错停止，已成功的语句保留结果。
- 可切换为「继续执行」（`stop_on_error = false`），每条结果独立展示。
- 结果区按语句分组，失败的语句高亮并显示错误码与位置。

### 2.2 补全

补全来源按优先级：

1. **当前上下文的表别名 → 列**（最能提升效率）。解析 SQL 的 `FROM`/`JOIN` 与别名，不依赖引擎。
2. 当前 schema 的表/视图名。
3. 引擎函数与关键字（按方言表）。
4. 用户片段（snippet）与历史查询中高频片段。
5. 字段注释（若元数据有）。

**规则**

- 输入 ≥ 2 字符或按 `Ctrl+Space` 主动触发。
- 候选必须**去重**并标注来源（表/列/函数/片段）。
- 表不存在时不要静默给空列表——给出「未找到，是否搜索全部 schema」。
- 不做「猜测意图改写 SQL」，只做补全。

**验收基准集**：维护一个 50 条真实 SQL 的补全基准（覆盖 join、子查询、CTE、窗口函数、Oracle 大写字面量），命中率 ≥ 90%。

### 2.3 高亮与校验

- 语法高亮用 Monaco 内置 SQL 方言 + 自定义关键字表（各引擎保留字差异必须体现：如 MySQL `ANALYZE` 是语句，PG 是命令）。
- **本地静态校验**（不发执行）：括号不匹配、未知表/列（基于缓存元数据）、明显语法错误。以波浪线提示，不阻断执行。
- **服务端校验**（可选）：`PREPARE` 或 `EXPLAIN` 空跑，仅对只读语句开放，避免副作用。

### 2.4 格式化

- 方言感知（关键字大小写策略、逗号位置、缩进宽度可配）。
- **格式化不得改变语义**：格式化后重新 `SplitStatements` + `Normalize`，与原文本指纹一致才算通过。不一致则拒绝应用并提示（说明格式化工具有 bug）。
- 字符串、注释、dollar-quote 内容原样保留。

## 3. 结果区

### 3.1 网格能力

| 能力 | 说明 |
|---|---|
| 虚拟滚动 | 只渲染可视区 ± 20 行；列宽超高时也虚拟化 |
| 分页加载 | 滚动到底自动取下一页（可关）；也可手动「加载更多」 |
| 列宽 | 自动按内容估算（限 400px），可手动调整，双击自适应 |
| 列固定 | 左侧固定列（便于看主键） |
| 排序 | 客户端排序仅对已加载页；「服务端排序」需重写查询（见 3.3） |
| 筛选 | 快速筛选（客户端，已加载数据）/ 条件筛选（服务端） |
| 选择 | 单元格、区域、整列、整行；`Ctrl+C` 复制为 TSV |
| 复制格式 | TSV / CSV / JSON / Markdown 表格 / SQL IN 列表 / INSERT 语句 |
| 空值与二进制 | `NULL` 与空串**视觉可区分**（`NULL` 灰斜体、`''` 显示为空）；二进制显示 `0x…` 与字节数 |
| 大字段 | 单元格截断显示，双击打开专用查看器（文本/JSON/图片/十六进制） |
| 类型保真 | `Decimal`/`BigInt` 以字符串传输，避免 JS 精度丢失 |

### 3.2 结果与语句的对应

- 每条语句一个结果集区块，标题显示语句前 60 字符 + 序号。
- 点击结果区块标题可跳回编辑器对应语句。
- 失败语句显示：错误码、引擎原生错误（脱敏）、出错位置（行列）、可执行建议。

### 3.3 服务端排序 / 筛选 / 分页的边界

**关键决策：不在结果集上做「二次查询改写」**。

原因：任意 SQL（含聚合、窗口函数、`UNION`、CTE）无法安全地包裹成子查询再排序，会因为列名冲突、类型、`ORDER BY` 位置出错。强行包裹会产生「看起来能用、特定查询就崩」的功能。

替代方案：

- **浏览表数据时**（来源是单表）：提供完整的服务端排序/筛选，因为此时 DBRover 自己生成查询。
- **执行自定义 SQL 时**：只有客户端排序/筛选（作用于已加载页），并在 UI 明确标注「仅对已加载 N 行生效」。
- 需要「对全量结果排序」→ 引导用户改写 SQL（提供「加 ORDER BY」快捷动作）或导出后处理。

这条边界必须写进 UI 文案，否则用户会以为排序是全量的。

## 4. 执行计划视图

### 4.1 三种视图

| 视图 | 用途 |
|---|---|
| **树** | 层级结构，节点显示操作、对象、估算/实际行数、耗时占比条 |
| **表** | 平铺，可按任意列排序（找最贵节点最快） |
| **原始** | 引擎原样输出（JSON/XML/文本），供专家核对 |

### 4.2 必须高亮的四种情况

1. **估算偏差**：`ActualRows / EstRows > 100` 或 `< 0.01` → 黄色，提示「统计信息可能过期」。
2. **全表扫描且行数大**：`SeqScan/COLLSCAN/ALL` 且 `ActualRows > 10000` → 橙色，提示「考虑索引」。
3. **嵌套循环内层大**：`NestedLoop` 且内层 `ActualRows > 10000` → 红色，提示「可能退化」。
4. **排序溢出**：`Sort` 带 `disk` 标记 → 提示「工作内存不足」。

### 4.3 安全约束

- `ANALYZE`（真实执行）**默认关闭**，且仅允许 `R0` 语句。写语句的 `ANALYZE` 一律禁止（会真的写数据）。
- 只在只读连接上允许 `ANALYZE`。
- `SHOWPLAN` 类设置必须在独立会话中开启并关闭，避免污染用户会话（MSSQL）。

### 4.4 计划缓存

同一连接内按 `sql_hash + 参数摘要` 缓存最近 20 个计划，避免重复执行昂贵语句。

## 5. 历史与收藏

| 项 | 规则 |
|---|---|
| 记录内容 | SQL 文本、连接、库、执行时间、耗时、状态、影响行数 |
| 不记录 | 结果集内容（除非用户显式开启快照） |
| 留存 | 默认 30 天或 1 万条，可配 |
| 检索 | 按连接/时间范围/关键字/是否失败 |
| 去重 | 相同 `sql_hash` 折叠展示，展开看每次执行 |
| 收藏 | 可命名、可分组、可导出 |
| 隐私 | 提供「清除最近 N 天历史」与「关闭历史记录」开关 |

**敏感数据**：SQL 里可能含身份证号等字面量。提供「历史脱敏」选项：存储时把字符串字面量替换为 `?`（保留归一化文本），原始文本不入库。默认开启。

## 6. 会话与事务面板

侧栏常驻，显示：

- 当前会话 id 与物理连接标识（便于对账）。
- 事务状态：`无` / `进行中 (开始于 12:03:41，已 4m12s)` / `已回滚`。
- 隔离级别（引擎默认值必须显式显示，因为 MySQL 与 PG 不同）。
- 会话级设置（`search_path`、`sql_mode`、`AUTOCOMMIT`）。
- 「提交」/「回滚」按钮 + 危险提示（未提交语句数）。
- 事务超时提醒：超过阈值（默认 5 分钟）标黄，超过 15 分钟标红并提示「长事务会阻塞 DDL」。

**自动提交语义**

| 引擎 | 默认 | DBRover 行为 |
|---|---|---|
| PG | autocommit | 保持；用户显式 `BEGIN` 才进事务 |
| MySQL | autocommit | 保持 |
| MSSQL | autocommit | 保持 |
| Oracle | autocommit（无 `BEGIN` 概念） | 保持，但 UI 明确「每条语句独立提交」 |
| SQLite | autocommit | 保持 |

**不做隐式事务**：工具不应把用户的 5 条语句偷偷包进一个事务——行为与用户预期不符，出错时回滚范围也难解释。

## 8. 长查询与资源

> **这一节一半是设计，一半是现状。** 取消入口已经有了（执行期间工具栏出现「取消」，
> 对应 `POST /connections/{id}/cancel`），但**没有**「已运行 N 秒」的计时、没有 30 秒提示、
> 也没有引擎侧等待事件展示。另外取消的实效性按引擎不同，见 §9 第 9 项。

- 超过 3 秒的查询：结果区显示「已运行 3s，可取消」，状态栏计时。**未实现**（取消按钮有，计时没有）
- 超过 30 秒：提示「是否继续等待 / 取消」，并显示当前会话在引擎侧的等待事件（若 `MonitorProvider` 可用）。**未实现**
- 结果行数超过 10 万：默认停止继续拉取，提示「已加载 10 万行，可继续或导出」。
- 单页大小默认 200 行，可配 50–2000。

## 9. 验收清单

| # | 项 | 判定 | 状态 |
|---|---|---|---|
| 1 | 光标在语句中间按 `Ctrl+Enter` 只执行该语句 | 手动 + 单测 | ✅ `TestStatementAt`、`TestExecuteRunsOnlyStatementAtCursor`、`TestExecWithCursorRunsOneStatement`（API 端到端）+ 浏览器实测（光标放在第 2 条语句里点执行，只跑了第 2 条，值未变）。**偏移由界面换算成 UTF-8 字节后再送**：`selectionStart` 是 UTF-16 码元下标，光标前有中文就会挑错语句 |
| 2 | 光标在两条语句之间执行前一条 | 单测 | ✅ `TestStatementAt`（空白处归前一条）、`TestCursorBetweenStatementsRunsPrevious` |
| 3 | 含 `;` 的字符串不被切开 | 表驱动单测（各引擎） | ✅ `dialect` 切分用例（dollar-quote / `DELIMITER` / `GO` / 嵌套注释） |
| 4 | 多语句中第 2 条失败，第 1 条结果保留且可见 | 集成 | ✅ 执行器逐条返回（成功那条带行数据、失败那条带 `err`，第 3 条不执行）；**接口侧以前会把已完成的结果丢掉**——现在错误体带 `error.results`，状态码仍是错误码、错误语义不变。界面在失败时先画已完成的结果再提示。用例：`TestMultiStatementKeepsEarlierResults`、`TestExecMultiStatementKeepsResultsOnError` |
| 5 | 100 万行结果翻页不 OOM，内存增长 < 200MB | 压测 | ✅ `TestMillionRowPagination`：100 万行表上按 200 行/页翻 60 页（1.2 万行），总耗时 619 ms、单页均摊 10.3 ms，**HeapAlloc 增长 1.7 MB**。断言只防「灾难性泄漏」（>200MB 才红），细微增长它抓不到 |
| 6 | 深分页第 10000 页 < 500ms（有主键表） | 基准 | ✅ `TestDeepKeysetPageLatency`：键集分页没有 OFFSET，「第 10000 页」的代价等价于「从很靠后的键取一页」——从 50 万行之后取 200 行，**13.1 ms**。不翻一万次是因为那测的是循环不是查询 |
| 7 | `Decimal(38,10)` 读回与写入完全一致 | 类型保真测试 | ✅ 见 `docs/06` 精度守卫与真机验收 |
| 8 | `NULL` 与 `''` 视觉可区分 | 视觉检查 | ✅ 界面用 `NULL` 标记区分；见 `docs/06` |
| 9 | 取消在 1s 内使引擎侧语句终止 | 集成（查 `pg_stat_activity` / `PROCESSLIST`） | ✅ 入口：执行期间工具栏「取消」→ `POST /connections/{id}/cancel`，客户端 1 毫秒内返回 `SQL_CANCELED`。真机三条都验过引擎侧真的停了：**PostgreSQL** `pg_sleep(30)` 取消后 `pg_stat_activity`（`state='active'`）1→0；**SQLite** interrupt 立刻停；**MySQL** `SLEEP(30)` 取消后 `processlist` 1→0（会话为此钉在单条物理连接上，另发 `KILL QUERY <id>`；只取消本地 ctx 不够，`SLEEP()` 不读 socket）。用例：`TestCancelStopsRunningQuery`、`TestCancelWhenIdleReturnsFalse`、`TestRunningClearedAfterNormalExecution`、`TestCancelSurvivesInterleavedQuery`、`TestCancelWhenIdle`（端点）、`TestCancelStopsStatementOnServer`（MySQL 真机，含变异验证：不发 KILL 就失败） |
| 10 | 执行计划对 5 种关系库可解析并高亮偏差节点 | 集成 | ⚠️ **3 个引擎已通过**：`POST /connections/{id}/explain` + 工具栏「计划」，支持 `cursor`；`AnalyzePlan` 把计划翻成偏差项并在计划表上方高亮——SQLite 认 `SCAN` / `USE TEMP B-TREE`，PostgreSQL 认 `Seq Scan` / `Nested Loop`，MySQL 认 `type=ALL` / `type=index` / `Using filesort` / `Using temporary`，同一条按 code+message 去重且最多 8 条。**未过**：MSSQL/Oracle 返回 400 `EXPLAIN_UNSUPPORTED`（没有镜像与实例），所以只有 3/5。用例：`TestExplainEndpoint`（断言 findings 里确有 FULL_SCAN）、`TestExplainUsesCursor`、`TestAnalyzePlan{SQLite,Postgres,MySQL,Dedupe,IgnoresUnknownEngines}`、浏览器实测。顺带修掉一个真 bug：`EXPLAIN QUERY PLAN` 被 `Analyze` 判成「无法识别 → 按写处理」 |
| 11 | 格式化后 `Normalize` 指纹不变 | 单测 | ✅ `dialect` 归一化用例 |
| 12 | 跨库引用（PG）在执行前被拦截并说明原因 | 单测 | ⚠️ 未做专门拦截；跨库查询会由引擎自己报错，错误信息原样返回 |

## 10. 已知取舍

| 取舍 | 理由 |
|---|---|
| 不对自定义 SQL 做服务端排序 | 任意 SQL 包裹不可靠，宁可明确边界 |
| 不默认记录结果集 | 隐私与体积；需显式开启 |
| 不做隐式事务包裹 | 行为可预期优先于「看起来方便」 |
| `ANALYZE` 默认关闭 | 会真实执行，写语句风险不可接受 |

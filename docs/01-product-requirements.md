# 01 · 产品需求文档（PRD）

> 状态：基线草案 v0.1 · 适用版本：v1 之前 · 需求编号全局稳定，可被 issue / 测试 / ADR 引用

---

## 1. 背景与问题

### 1.1 现实

一个中等规模的技术团队通常同时存在 3–6 种数据库：业务主库（MySQL 或 PostgreSQL）、报表/分析库（PostgreSQL / ClickHouse）、遗留系统（SQL Server / Oracle）、缓存与队列（Redis）、文档存储（MongoDB）、搜索（Elasticsearch）。这不是技术选型失误，而是业务演化的自然结果。

### 1.2 现有工具的四个断点

| 断点 | 表现 | 后果 |
|---|---|---|
| **工具割裂** | 每种库一个客户端，快捷键、术语、交互全不同 | 认知负担高，新人上手慢 |
| **变更无保护** | 「保存」即执行，无影响预估、无回滚语句、无审批 | 一次误操作造成生产事故 |
| **AI 是外挂** | 聊天窗口吐 SQL，人工复制粘贴，模型看不到真实 schema | 生成的 SQL 经常跑不通，或跑通了但语义错 |
| **不可审计** | 谁在什么时候改了哪张表，只能翻 binlog 或问人 | 事故复盘困难，合规无法交付 |

### 1.3 DBRover 的判断

这四件事的根因是同一个：**能力没有被收敛成受控的、可描述的接口**。

一旦「执行一条 SQL」变成一个有明确输入、输出、风险等级、审计记录的 API 调用，那么：

- UI 可以任意重组（多引擎统一语义）；
- Agent 可以安全地复用同一能力（不必另造一套）；
- 审计天然成立（所有路径都过同一个门）；
- 变更安全可以在门上加检查，而不是在 20 个按钮上各加一遍。

**因此产品设计与架构设计在此高度重合**：先定义能力面，再定义界面。

## 2. 目标与非目标

### 2.1 目标（v1）

1. 覆盖 8 种引擎的**连接、浏览、查询、编辑**主链路，其中关系库达到「日常可替代 dbForge/DBeaver」的完成度。
2. 把「改动生产数据或结构」变成**可预览、可审批、可回滚**的流程。
3. 让 AI Agent 能在**不需要人工搬运 SQL** 的前提下完成 80% 的日常数据库任务，且每一步可审计。
4. 单机零部署可用；同一份核心支持团队服务化。

### 2.2 非目标（明确不做）

| 不做 | 理由 |
|---|---|
| BI 报表 / 图表分析 | 与 Metabase/Superset 重叠，不是本产品的护城河 |
| 持续数据同步 / CDC 管道 | 只做一次性迁移与手动触发的增量搬运，不做常驻同步服务 |
| APM / 应用链路追踪 | 只做数据库视角的观测，不侵入应用 |
| 数据库内核或代理层 | 不改协议、不劫持流量（SSH 隧道除外） |
| 多人实时协同编辑 | v1 不做；仅支持查询与 Runbook 的共享（快照式） |
| 云厂商托管控制台替代 | 不做实例创建、扩容、计费 |

## 3. 角色与画像

| 角色 | 代号 | 典型诉求 | 关键约束 |
|---|---|---|---|
| 后端工程师 | `ENG` | 查数据、改数据、加字段、看执行计划 | 不熟 DBA 细节，怕改坏生产 |
| DBA / SRE | `DBA` | 慢查询、会话、锁、备份、容量 | 对权限与审计极敏感 |
| 数据工程师 | `DE` | 跨库搬运、结构比对、批量修数 | 数据量大，要求可断点续跑 |
| 技术负责人 | `TL` | 快速理解陌生库、评审变更、追责 | 时间碎片化，要「一眼看懂」 |
| 团队新人 | `NEW` | 不知道表在哪、字段什么意思 | 需要可发现性与解释 |
| AI Agent | `AGT` | 结构化访问 schema 与执行能力 | 必须受权限与审批约束 |

> `AGT` 被列为角色而非工具：它有自己的入口、权限、审计身份与失败模式。

## 4. 核心场景（JTBD）

每个场景写清「触发 → 现状 → DBRover → 验收」。验收标准直接映射到需求编号。

### S1 · 线上慢了，先看哪儿

- **触发**：告警说接口 P99 涨到 3s。
- **现状**：登录跳板机，连库，`SHOW PROCESSLIST` 看不到历史；翻监控平台对不上时间点。
- **DBRover**：打开连接 → 性能面板直接给出「近 15 分钟 Top 慢 SQL（按总耗时排序）+ 对应会话 + 锁等待链」，点一条慢 SQL 直接进编辑器并带出 `EXPLAIN`。
- **验收**：从打开应用到看到目标慢 SQL 的执行计划，操作步数 ≤ 4；`FR-MON-01/03`、`FR-SQL-07`。

### S2 · 加一个字段，别出事

- **触发**：需求要给 `order` 表加 `channel_code`。
- **现状**：手写 `ALTER TABLE`，不确认表多大、有没有长事务、能不能回滚。
- **DBRover**：结构设计器改字段 → 生成 `Change Plan`：DDL 语句、预估锁时长与影响行数、在线 DDL 可行性提示、回滚语句 → 确认后执行，执行期间展示进度。
- **验收**：任何 `R3` 及以上操作必须展示回滚语句才能点执行；`FR-SCH-05`、`FR-SEC-04`。

### S3 · 修一批脏数据

- **触发**：`status` 字段被写成了 `'1'` 而不是 `1`，影响 3000 行。
- **现状**：写个 `UPDATE`，先 `SELECT COUNT(*)` 确认，再执行，提心吊胆。
- **DBRover**：在数据网格里筛选 → 批量编辑 → 提交前弹出「影响 3000 行，示例 5 行前后对比，回滚 SQL 已生成」→ 确认 → 执行并按事务分批。
- **验收**：批量修改必须有前后对比与回滚语句；`FR-DATA-06/07`、`FR-SEC-03`。

### S4 · 把 A 库的表搬到 B 库

- **触发**：分库拆分，需要把 12 张表从 MySQL 搬到 PostgreSQL。
- **现状**：`mysqldump` + 手工改语法 + 逐张表校验，几天工作量。
- **DBRover**：迁移向导选源/目标 → 自动类型映射（含冲突项高亮）→ 预检（字符集、时区、自增、NULL 语义）→ 分批搬运（可暂停/续跑）→ 行数与校验和比对报告。
- **验收**：中断后可续跑且不重复插入；结束时给出逐表行数与 checksum 差异清单；`FR-MIG-01..05`。

### S5 · 摸清一个陌生库

- **触发**：接手遗留系统，只有连接串。
- **现状**：挨个 `SHOW TABLES`、`DESC`，靠猜外键关系。
- **DBRover**：连接后自动生成「库画像」：表数量与体量分布、核心实体（按入度）、孤立表、无主键表、缺失索引的外键、最近变更对象；点任意表可看 ER 邻域。
- **验收**：连接后 10s 内给出画像首屏；无主键表与缺索引外键必须列出；`FR-META-06`、`FR-SCH-08`。

### S6 · 让 AI 帮我把这件事做完

- **触发**：「帮我看下最近 7 天支付失败的订单，按失败原因分组，找出异常突增的那一类，然后告诉我是哪张表哪个字段的问题。」
- **现状**：自己写 SQL、自己反查 schema、自己推断。
- **DBRover**：Agent 在只读模式下自主完成：读 schema → 生成 SQL → 执行 → 观察结果 → 迭代 → 给结论，并把每一步的 SQL 与结果摘要展示出来；涉及写操作时停下请求授权。
- **验收**：完整链路无需人工复制 SQL；每步可展开查看实际执行的语句；写操作 100% 触发审批；`FR-AGT-01..08`。

### S7 · 备份到底有没有用

- **触发**：季度演练要求「从备份恢复一个库，并在 4 小时内验证可用」。
- **现状**：备份任务在运维平台，恢复没人敢试。
- **DBRover**：备份计划 + 一键恢复到临时实例/临时库 → 恢复后自动跑校验（表数、行数抽样、索引可用性）→ 输出演练报告。
- **验收**：恢复目标默认为「新库/新实例」，禁止覆盖源库（除非 R4 双确认）；`FR-BAK-04/05`。

## 5. 能力需求池

优先级：`P0` v1 必须 · `P1` v1.x · `P2` 后续。

### 5.1 连接与工作区

| 编号 | 需求 | 优先级 | 验收 |
|---|---|:--:|---|
| FR-CON-01 | 支持 8 种引擎的连接创建，表单按引擎动态变化（Oracle 需区分 SID/Service Name） | P0 | 8 种引擎各至少一条成功连接用例 |
| FR-CON-02 | 连接配置可分组、可导入导出（凭据单独处理，导出不含密码） | P0 | 导出文件不含明文凭据；导入后需重新输入密码 |
| FR-CON-03 | 连接测试给出**可诊断**的失败原因（DNS/端口/认证/库不存在/TLS/时区） | P0 | 每类失败有独立错误码与修复建议 |
| FR-CON-04 | 支持 SSH 隧道（密码/私钥/agent），支持跳板机多跳 | P0 | 2 跳场景可连通；私钥口令可保存 |

## 7. 竞品定位

| 维度 | dbForge Studio | DBeaver | DataGrip | Navicat | DBRover |
|---|---|---|---|---|---|
| 引擎数量 | 分产品线，单引擎为主 | 极广（JDBC） | 广 | 广 | 8 种，关系库深、NoSQL 运维向 |
| AI | 有辅助 | 插件/有限 | 有 AI Assistant | 弱 | **Agent 原生，与人工同权限面** |
| 变更安全 | 有 schema compare | 弱 | 有 | 中 | **Change Plan + 回滚 + 影响预估** |
| 审计 | 无 | 无 | 无 | 无 | **全链路不可变审计** |
| 部署 | Windows 桌面 | Java 桌面 | Java 桌面 | 桌面 | 单二进制桌面 + 可服务化 |
| 跨引擎语义 | 不统一 | 部分统一 | 较好 | 部分统一 | **统一四层模型 + 能力降级显式化** |

**差异化不靠「功能更多」，靠「同一件事更安全、更可解释」。** 因此所有功能都要回答两个问题：这一步失败了会怎样？我怎么知道它真的成功了？

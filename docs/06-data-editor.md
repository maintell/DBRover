# 06 · 数据浏览与编辑

> 需求编号：`FR-DATA-01..10`。核心命题：**让「改一行数据」既顺手又不留隐患。**

---

## 1. 浏览

### 1.1 打开方式

| 入口 | 生成查询 |
|---|---|
| 双击表 | `SELECT <列清单> FROM <表> ORDER BY <主键> LIMIT <page>` |
| 右键 → 查看数据 | 同上 |
| 表详情 → 数据页 | 同上 |

**必须显式生成列清单**，不用 `SELECT *`。理由：`SELECT *` 在宽表（200 列）时传输浪费，且列顺序变化会让「按位置映射」出错。

### 1.2 无主键表

- **只读**，UI 顶部常驻提示：「该表无主键，无法安全定位行，已禁用编辑」。
- 仍可浏览、筛选、导出。
- 提供「为什么」解释：没有唯一标识时，`UPDATE ... WHERE` 可能命中多行；即便引擎给了 `ctid`/`rowid`，它也会在 `VACUUM`/页重组后失效，本质不安全。

### 1.3 视图与物化视图

- 视图默认只读（是否可更新取决于引擎与视图定义，不尝试推断）。
- 提供「尝试编辑」开关：开启后由引擎报错兜底，错误如实展示。

### 1.4 大字段与特殊类型

| 类型 | 展示 | 编辑 |
|---|---|---|
| 长文本 | 截断 200 字符 + 展开 | 专用编辑器（等宽字体、可搜索） |
| JSON/JSONB | 折叠摘要（键数量、字节数） | JSON 编辑器 + 格式化 + 校验 |
| 二进制/BLOB | `0x…（N 字节）` | 十六进制编辑器 / 上传文件 / 下载 |
| 图片（按魔数识别） | 缩略图 | 只读预览，替换走上传 |
| 数组（PG） | `{a,b,c}` | 逐元素编辑 |
| 几何 | WKT 文本 | 文本编辑（不画图） |
| 枚举/集合 | 下拉（取元数据枚举值） | 下拉，允许输入非标准值并警告 |
| 时间戳 | ISO8601 + 时区标注 | 日期时间选择器 + 手动输入 |

**时区规则**：所有 `timestamptz` / `TIMESTAMP WITH TIME ZONE` 统一以 UTC 传输，按连接配置的 `display_timezone`（IANA 名，空 = UTC）渲染。`timestamp`（无时区）不转换，原样显示并标注「无时区」。这条必须写进 UI 文案，否则用户会误判。

实现上分两层，缺一层就会静默挪时间：

| 层 | 做法 | 不做会怎样 |
|---|---|---|
| 存储 | 握手时把会话时区钉成 UTC（MySQL `time_zone='+00:00'`、PG `timezone=UTC`） | MySQL 的 `TIMESTAMP` 在 SELECT 时按会话时区换算，会话是 +08:00 而驱动按 `loc=UTC` 解析，取出来整体偏 8 小时 |
| 展示 | 驱动返回行时按 `display_timezone` 换算 `time.Time`，所有读路径共用这一个点 | 表浏览、导出、游标续页各自为政，同一条数据显示成两个时间 |

写回时按列类型归一（`normalizeTemporal`）：带时区的列换算到 UTC 保住瞬间；不带时区的列保留墙上时钟，保住用户看到的 12:00；`DATE`/`TIME` 取字面值，不跨零点。另外，接口读出去的是带偏移的 RFC3339，原样写回 MySQL 会报 `1292 Incorrect datetime value`——「读出来再存回去」这条路必须先归一才通。

## 2. 变更集模型（Change Set）

**这是本模块的核心设计。**

### 2.1 为什么不是「改一格存一格」

逐格提交的问题：

- 一次改 10 格 = 10 次网络往返 + 10 个事务，慢且不原子。
- 中间失败会留下半改状态，用户无法判断哪些生效了。
- 无法预览「将要执行什么」。

### 2.2 模型

```go
type ChangeSet struct {
    ID       string
    Table    ObjectRef
    Entries  []Entry
    BaseTx   bool      // 是否单事务提交
}

type Entry struct {
    Op      Op                // insert | update | delete
    Key     RowKey            // 主键值（insert 时为空）
    Before  map[string]Value  // update/delete：原值（仅用于并发校验与回滚生成）
    After   map[string]Value  // insert/update：新值
    Dirty   []string          // 实际变化的列（避免整行 UPDATE）
}
```

**UI 行为**

- 编辑单元格 → 进入「未提交」视觉态（角标颜色 + 行首标记）。
- 顶部出现变更条：`3 处修改 · 1 行新增 · 查看 / 提交 / 丢弃`。
- 关闭标签页时若有未提交变更 → 拦截确认。

### 2.3 提交语义

```
提交
 ├─ 生成 SQL 预览（可展开逐条）
 ├─ 影响面估计（行数、涉及表）
 ├─ 事务能力?
 │   ├─ 支持且 entries ≤ 500 → 单事务提交（原子）
 │   └─ 不支持或 > 500 → 分批提交，逐批落检查点，失败可续
 └─ 执行 → 逐条校验影响行数 → 报告结果
```

**决策：默认单事务，阈值按环境分档**（见 §6 取舍表）。

| 连接环境 | 单事务阈值 | 超出后行为 |
|---|:--:|---|
| `local` / `test` | 5000 条 | 分批，无额外提示 |
| `staging` | 2000 条 | 分批 + 提示 |
| `production` / `unknown` | 500 条 | 强制分批 + 弹窗确认（`F2`）+ 显示每批进度 |

环境同时决定**是否需要确认**：测试库上提交变更集是 `F1`（内联预览，点提交即走），生产库的批量改动是 `F2`（弹窗含前后对比与回滚）。规则见 [`10-connection-and-security.md`](10-connection-and-security.md#52-摩擦分级环境--风险)。

**影响行数校验**

每条 `update`/`delete` 执行后必须检查 `RowsAffected == 1`：

- `== 1` → 成功
- `== 0` → **并发冲突**（行已被他人改或删）→ 整批回滚，高亮冲突行，提示「该行已被修改，请刷新后重试」
- `> 1` → **定位不唯一**（理论上不该发生，说明主键判定有误）→ 整批回滚 + 报缺陷级错误

### 2.4 乐观并发控制

`UPDATE` 的 `WHERE` 用**原值**而非仅主键：

```sql
UPDATE "order"
   SET "status" = $1, "updated_at" = $2
 WHERE "id" = $3
   AND "status" = $4          -- 原值
   AND "updated_at" = $5      -- 原值
```

- 只对**被修改列的原值**做校验（不是全列），减少误判。
- `NULL` 用 `IS NOT DISTINCT FROM` / `<=>`（MySQL）/ `IS NULL` 组合处理。
- 浮点数与 `bytes` 不做原值校验（精度不可靠），只用主键，并在提示中说明「该列不做冲突检测」。
- 无主键表已在浏览层禁用编辑，此处不需要兜底。

### 2.5 生成的 SQL 形态

| 操作 | SQL |
|---|---|
| update | `UPDATE t SET <仅变更列> WHERE <主键> AND <原值校验>` |
| insert | `INSERT INTO t (<列>) VALUES (<参数>)`；自增列不传，返回生成值回填网格 |
| delete | `DELETE FROM t WHERE <主键> AND <原值校验>` |

所有值走参数化，**不做字符串拼接**（除了标识符，经 `QuoteIdent`）。

### 2.6 回滚

提交成功后生成反向 `ChangeSet`（保存在会话内，10 分钟内可一键撤销）：

| 原操作 | 回滚 |
|---|---|
| update | `UPDATE ... SET <旧值> WHERE <主键>` |
| insert | `DELETE WHERE <主键 = 返回的自增值>` |
| delete | `INSERT <完整旧行>` |

**回滚的能力边界（必须在 UI 说明）**

- 回滚是**补偿**，不是数据库层面的 undo。
- 若期间有触发器、外键级联、其他写入，回滚可能失败或不完整。
- 生成列、`DEFAULT` 表达式列、`IDENTITY` 列在 delete→insert 回滚中可能无法完全还原。
- 超过可逆窗口（10 分钟或会话关闭）后按钮消失。

### 2.6.1 撤销的实现口径

**撤销不开后门。** 应用成功后，服务端把预案里已算好的反向语句登记成**另一张普通预案**（ID 前缀 `undo-`），撤销就是把它 POST 回同一个 `apply` 端点。因此：

| 问题 | 答案 |
|---|---|
| 撤销要不要过风险分级与审批？ | 要。它是一张普通预案，沿用同样的 `risk` / `friction`，生产库上同样要求审批 |
| 撤销受 10 分钟限制吗？ | 受。`undoTTL = 10min`，过期后 `apply` 返回 404 |
| 能撤销「撤销」吗？ | 不能。撤销预案带 `undo: true`，应用后不再生成新的撤销预案 |
| 不可逆的变更怎么办？ | 应用响应里 `undo` 为 `null`（例如 delete 未带整行原值、insert 缺自增主键回填）。**改不回来就说改不回来**，不给一个点了会失败的按钮 |
| 页面刷新后还能撤销吗？ | 不能。撤销入口只存在于本次界面状态；预案本身在服务端有效期内仍可被 `apply`，但用户侧看不到入口 |

反向语句的 `expect_rows` 与正向一致（都是 1），所以撤销同样受「影响行数不符即整体回滚」保护——期间别人又改了这行，撤销会报冲突而不是覆盖。

## 3. 批量修改

### 3.1 两条路径（必须区分）

| 路径 | 语义 | 适用 |
|---|---|---|
| **多单元格编辑** | 选中同列的多行 → 输入值 → 全部改为该值（走 ChangeSet） | 手工选定，行数少 |
| **条件批量修改** | 按筛选条件生成 `UPDATE ... WHERE`，**不加载行** | 行数不可预知，可能上万 |

UI 上是两个不同入口，文案必须区分「修改选中的 12 行」与「修改符合条件的全部行」。

### 3.2 条件批量修改流程

```
设定条件（可视化构建器或原始 WHERE）
  → 估算影响行数
      · 优先：SELECT COUNT(*) FROM t WHERE <cond> LIMIT <阈值+1>
      · 兜底：EXPLAIN 的行数估算（标注"估算值"）
  → 展示：将修改 N 行（或 ≥ N，若为估算）
  → 展示：示例前后对比（5 行）与回滚 SQL
  → 风险分级 R2 → 需确认
  → 执行（分批：每批 1000 行，按主键区间推进，可中止）
```

**关键约束**

- 无条件（空 `WHERE`）的批量修改 → 直接判定 `R4`，要求输入表名确认。
- 影响行数 > 1000 时分批执行：每批 1000 行，按主键键集推进，界面显示进度与「已提交 N 行」实时计数，可中止。
- 中止后已提交批次不自动回滚；结果里如实报出已提交行数，预案保留，可重新提交改完剩余行。

**为什么阈值是 1000 而不是 10000**：1000 正是逐行回滚的生成上限（§3.3）。超过它就已经拿不到回滚语句，此时再要求「一个事务改完 N 万行」只会同时放大三件事——锁持有时间、回滚日志体积、失败时要重来的量。用一个数字同时表达「没有回滚」与「必须分批」比两个数字更好记，也更难配错。

**复合主键怎么推进**：键集条件按列展开成 OR，不用行值比较（`(a,b) > (?,?)` 在 SQLite 3.15 之前不可用，而展开式在三个引擎上都是普通布尔表达式）：

```sql
-- 下一批：a 更大，或 a 相同而 b 更大
(a > ?) OR (a = ? AND b > ?)
```

代价是「按主键定位」那一半也要写成 `(a=? AND b=?) OR (a=? AND b=?) …`，每多一组就多两层表达式，而 SQLite 的表达式树深度上限是 1000（`SQLITE_MAX_EXPR_DEPTH`）。所以**复合主键的批大小降到 200**（单列主键仍是 1000，用 `IN (...)` 只有一个节点，不吃深度）。

这两档是实测出来的：先用 1000 跑，SQLite 直接报 `Expression tree is too large (maximum depth 1000)`。

### 3.3 回滚 SQL 的体积问题

大批量修改的回滚 SQL 可能比数据本身还大。策略：

- 影响 ≤ 1000 行：生成完整回滚语句并存于会话。
- 影响 > 1000 行：不生成逐行回滚，改为**备份受影响主键与旧值到临时表**（同库或本地），提示「已生成回滚快照表 `<schema>._dbrover_undo_<ts>`，保留 24 小时」。
- 用户可选择「不生成回滚」以换取速度，但需显式勾选，风险等级升为 `R4`。

### 3.4 v1 已实现口径（比上面窄，差距写清）

§3.1–§3.3 是目标形态。已实现的是「条件批量修改」这条路径：

| 项 | v1 做法 | 与目标的差距 |
|---|---|---|
| 入口 | 数据工具条「批量修改」：选列 → 填新值 → 按**当前筛选条件**一次改多行 | 无「多单元格选同列改同值」的批量路径（行内编辑仍逐格） |
| 影响面 | 生成预案前用 `COUNT(*)` **精确统计**，写进 `expect_rows`；不分批时执行行数必须完全一致，不符即整体回滚 | 与目标一致 |
| 空 `WHERE` | 判定为全表写，**必须回填表名**才允许生成预案（否则 `ErrBulkNeedsConfirmTable`）；风险由策略判为 `R4` | 与目标一致（验收 9） |
| 前后对比 | 展示最多 5 行的 `{主键} 改前 → 改后` | 与目标一致 |
| 回滚 | 有主键且影响 ≤ 1000 行时**逐行生成反向 UPDATE**；超过 1000 行不生成，标不可逆并要求显式接受（`accept_no_rollback`） | 目标要求 >1000 行走 undo 临时表；v1 直接不生成并要求显式确认 |
| 分批 | 影响 > 1000 行时按主键键集分批（每批独立事务、批间可中止），`apply?stream=1` 用 NDJSON 回报进度。单列主键每批 1000 行；**复合主键也支持**，键集条件按列展开成 OR，批大小降到 200（SQLite 表达式树深度上限 1000） | 与目标一致，只是阈值取 1000 而非 10000 |
| 主键列 | 禁止批量修改 | 与目标一致（主键是行定位依据） |

**分批的实现口径**

| 问题 | 答案 |
|---|---|
| 怎么挑下一批？ | `SELECT pk FROM t WHERE <原条件> AND pk > <上批末值> ORDER BY pk LIMIT 1000` |
| 为什么不「改完再查一遍」？ | 若筛选条件与被改列无关，改过的行仍然命中，重查会在原地打转 |
| 为什么不用 `UPDATE ... WHERE pk > 上批末值`？ | 那会越过本批边界，把后面还没数过的行一起改掉。键集只用来**挑行**，改行仍然是 `WHERE pk IN (...)` |
| 每批一个事务还是一个大事务？ | 每批一个独立事务。两万行的长事务在 MySQL 上长时间持锁，中途失败还要全部重来 |
| 中途失败怎么办？ | 该批回滚（批内原子），之前的批保留。结果里的 `rows_affected` 是真实已提交行数，错误信息里带上这个数字 |
| 中止（`ctx` 取消 / 点「停止」）怎么办？ | 在批与批之间停下，已提交的批不回滚，返回 `409 CHANGE_APPLY_ABORTED`，**预案不删除**——`SET` 是常量，重新提交是幂等的，可以把剩下的行改完 |
| 分批时还能撤销吗？ | 不能。影响 > 1000 行本来就不生成逐行回滚，`undo` 返回 `null` |

## 4. 筛选与排序

### 4.1 可视化构建器

- 支持：`=` `≠` `>` `≥` `<` `≤` `IN` `BETWEEN` `LIKE` `IS NULL` `正则`（引擎支持时）
- 组合：AND / OR，可分组（一层嵌套）
- 与原始 SQL 模式双向切换：切到原始模式后不可回退（避免解析任意表达式）
- 条件持久化到标签页，刷新保持

### 4.2 排序

- 多列排序（优先级可见、可拖拽）
- 无主键表排序后仍只读
- 排序键变化 → 重置分页游标（keyset 参数变了）

### 4.3 v1 已实现口径（比上面窄，差距写清）

§4.1 / §4.2 是目标形态。已实现的部分刻意做窄，理由是**筛选项与排序列必须来自服务端已知的列**，前端不猜、也不拼 WHERE 片段：

| 项 | v1 做法 | 与目标的差距 |
|---|---|---|
| 条件组合 | 仅 `AND` | 无 `OR`、无分组 |
| 操作符 | `=` `≠` `>` `≥` `<` `≤` `LIKE` `IN` `BETWEEN` `IS NULL` `IS NOT NULL` | 无正则（跨引擎语义不一致）。`IN`/`BETWEEN` 用 `values` 数组传值，不用「逗号拼进 value」——值里本身带逗号是真实数据 |
| 原始 SQL 模式 | 不做 | 允许手写 `WHERE` 就必须做表达式校验，否则等于开了注入面 |
| 排序 | 单列 + 升降序；主键**始终**追加在排序键末尾 | 无多列拖拽 |
| 分页 | 键集分页；`after` 是「排序列…, 主键…」的完整元组 | 与目标一致 |
| 页大小 | 100 / 200 / 500 / 1000 | 与目标一致 |

**为什么主键必须留在排序键里**：只按非唯一列排序时，`WHERE (sort) > (? LIMIT 1)` 会在重复值边界上漏行或原地打转。追加主键后排序键成为全序，`(sort, pk…) > (?, ?…)` 才有确定的下一页。

**降序时所有排序键同向**：`ORDER BY sort DESC, pk DESC`，比较符取 `<`。混向会让行构造器比较失效。

**接口形状**

```
GET /api/v1/connections/{id}/tables/{name}/rows
    ?limit=100
    &where=[{"column":"score","op":"ge","value":"30"}]
    &order={"column":"score","desc":true}
    &after=["99","1"]
```

- 列名必须在表定义中，否则 `400 FILTER_INVALID`（不是 500：写错列名是请求问题）。
- 操作符不在白名单同样 `400 FILTER_INVALID`。
- 比较值按列类型还原（整型列不会拿字符串去比）；`LIKE` 例外，它只对文本有意义。

**降级行为**：筛选结果为空时正常返回 0 行，不报错；`after` 长度与排序键不一致时忽略该参数（当作第一页），避免因前端状态错乱导致整页空白。

## 5. 导出与数据生成

### 5.1 导出

| 格式 | 说明 |
|---|---|
| CSV | 可配分隔符、引号、换行符、是否含表头、编码（UTF-8 / UTF-8 BOM / GBK） |
| JSON | 数组或 NDJSON；`Decimal`/`BigInt` 以字符串输出保留精度 |
| Excel (xlsx) | 流式写入，避免内存爆；单 sheet 上限 104 万行，超出分 sheet |
| SQL INSERT | 分批语句，可选方言与批大小 |
| Markdown 表格 | 便于贴文档 |

**流式导出**：不走「先加载全部再写文件」，而是服务端边读边写，UI 显示进度与取消。

### 5.1.1 v1 已实现口径（比上面窄，差距写清）

§5.1 是目标形态。已实现的部分只做三种格式，但把「流式」与「精度」这两件容易错的事做对了：

| 项 | v1 做法 | 与目标的差距 |
|---|---|---|
| 格式 | `csv`、`ndjson`（每行一个 JSON 对象）、`sql`（建表 + `INSERT`，可回放的脚本） | 无 xlsx、Markdown；`sql` **只保证同引擎回放**，不做跨引擎类型映射 |
| 流式 | 单条 `SELECT` 走游标分批取，内存上限由 `page_size`（≤1000）决定；边取边写 | 与目标一致 |
| 与筛选/排序联动 | 复用 `where` / `order`，导出的就是**当前视图**（不受分页限制） | 与目标一致 |
| 主键要求 | **不要求**。视图与无主键表也能导（浏览才必须键集分页） | 与目标一致 |
| CSV 的 NULL | 写成空单元格 | CSV 没有 NULL 表示法，与空字符串在文本上不可区分；要区分请用 ndjson |
| JSON 的大整数 | `int64` 一律以字符串输出 | 与目标一致（JSON 数字在多数语言里按双精度解析，超过 2^53 静默丢精度） |
| 二进制 | base64；CSV 里是合法 UTF-8 才按文本写 | 与目标一致 |
| `sql` 的字面量与边界 | 字面量按方言写：二进制 `X'..'`（MySQL/SQLite）与 `'\x..'::bytea`（PG）、布尔 `1/0` 与 `TRUE/FALSE`、字符串单引号双写、时间 `'YYYY-MM-DD HH:MM:SS'`；脚本头部带「同引擎回放」的说明 | 跨引擎要先做类型映射，不在这个格式的承诺内；它服务的是「把一张表搬到另一个同引擎库」，与 `docs/08` 的逻辑备份方向一致 |
| 失败处理 | 响应头推迟到第一次写出数据时才发；开跑前失败返回结构化 JSON 错误，不会给出空文件配 200 | 与目标一致 |
| 导出行数 | 只在审计里记录（流写完才知道行数，那时响应头早已发出） | 与目标一致；不要指望响应头带行数 |

**压测记录**（2026-11-03，本地 SQLite，`page_size` 默认 500）：

| 指标 | 结果 |
|---|---|
| 行数 | 1,000,000（+1 行表头） |
| 产物 | 19.7 MB CSV |
| 耗时 | 1.5 s |
| 进程工作集 | 12.1 MB → 22.7 MB（增长 **10.6 MB**，要求 < 200 MB） |
| 完整性 | 末行 `1000000,row-1000000,27`；第 50 万行抽样正确；无重复无截断 |

**界面入口**：表工具条「导出」+ 格式下拉，按当前筛选与排序导出整表。界面走 `fetch` 拿 Blob 再交给浏览器保存——接口要 `X-DBRover-Token` 请求头，普通链接带不上。代价是文件先落在浏览器内存里，**千万行级别的导出请用 CLI / curl** 走真正的流式；状态栏显示「已取回 + 字节数 + 首行」，用于确认内容确实取回（文件落盘由宿主浏览器负责）。

### 5.2 生成测试数据（`P2`）

- 按列类型与约束生成：整数范围、字符串长度、枚举取值、外键从目标表随机取样、唯一约束去重。
- 支持指定行数与批量插入。
- 明确警示：仅在非生产连接可用（`access_mode != read-only` 且连接标记非生产）。

## 6. 取舍

| 决策 | 选择 | 理由 |
|---|---|---|
| 事务粒度 | 单事务；阈值按环境分档（test 5000 / staging 2000 / prod 500） | 阈值内原子性可控且不会长时间持锁；超出后长事务危害更大 |
| 无主键表 | 只读 | `ctid`/`rowid` 不可靠，安全优先 |
| 视图编辑 | 默认只读 | 可更新视图的判定因引擎/定义而异，推断必错 |
| 列清单 | 显式，不用 `*` | 宽表性能与列序稳定 |
| 冲突处理 | 报冲突，不覆盖 | 静默覆盖是数据事故的主要来源 |
| 批量回滚 | 大影响转 undo 表 | 逐行回滚 SQL 体积不可控 |
| 浮点原值校验 | 跳过 | 精度不可靠，做了也是假安全 |

| 10 | 导出 100 万行 CSV 内存增长 < 200MB | 压测 | 过：本地 SQLite 100 万行，19.7 MB CSV / 1.5 s，进程工作集 12.1 → 22.7 MB（增长 10.6 MB）；文件首尾与抽样行均正确 |
| 11 | 时区：`timestamptz` 按配置时区显示，写回为 UTC | 集成（跨时区样例） | 过：真实 MySQL 5.7.38（`TIMESTAMP`）与 PostgreSQL 17.11（`timestamptz`）各建两条连接读同一行——`display_timezone=Asia/Shanghai` 读到 `2026-11-03T12:00:00+08:00`，默认连接读到 `2026-11-03T04:00:00Z`，两者解析后是同一瞬间；把值改成 `2026-11-03T05:30:00+08:00` 写回后，UTC 连接读到 `2026-11-02T21:30:00Z`，说明存的是瞬间、展示才换算。顺带修掉两处会让时间静默挪 hour 的缺陷（会话时区没钉 UTC、接口读出的 RFC3339 原样写回被 MySQL 拒绝） |
| 12 | 关闭未提交变更的标签页被拦截 | 手动 | 过：浏览器实测 A/B（有改动跳转被拦、丢弃后同一跳转成功） |
